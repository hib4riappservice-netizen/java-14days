# 15日目以降：本当に「優秀」と言われるための6ヶ月ロードマップ

## まず、14日目のあなたの現在地

14日間を終えたあなたは、こうなっているはずです。

**できること**
- 小さな機能を仕様から一人で作り切れる
- レイヤードアーキテクチャの型に沿って書ける
- テストが書ける、Gitが使える、レビューが受けられる
- エラーを自力で調査できる

**まだできないこと（これが正常です）**
- 大規模な既存コード（10万行）を読み解く
- 「型に沿って書く」から「なぜその型なのかを踏まえて外す判断をする」
- 性能問題を実測から特定・改善する
- 障害対応（深夜にシステムが止まったときに動ける）
- 要件が曖昧な段階から設計を組み立てる
- 他人のコードをレビューして育てる

**14日間で身についたのは「型」です。「型を破る判断力」は経験の量でしか手に入りません。**
以下は、その経験を最短で積むための順路です。

---

## 第1〜2ヶ月：現場のコードに溺れる期間

### やること
1. **配属先の既存コードを毎日読む（1日1時間、必ず）**
   - `Ctrl+B`（定義へジャンプ）と `Alt+F7`（使用箇所検索）を武器に、1つのリクエストが Controller → Service → Repository → DB とどう流れるかを追う
   - **読んだら図に描く**。頭の中だけで理解した気にならないこと
   - 分からない設計判断は、メモして週1でまとめて先輩に聞く

2. **小さいチケットを大量にこなす**
   - 「バグ修正」「文言変更」「項目追加」から始まります。これは軽視されがちですが、**既存コードを読む最良の訓練**です
   - 1チケットごとに「このコードはなぜこうなっているのか」を1つ以上考える

3. **障害対応の見学をする**
   - 先輩が障害を調べているとき、横で見せてもらう。**ログの追い方は現場でしか学べません**

### この期間の目標
- 担当システムの主要な処理フローを、図を描いて説明できる
- 小さいチケットを、質問1回以内で完了できる
- ログを見て「どこで何が起きたか」を追える

### 学習リソース
- 『**リーダブルコード**』（オライリー）— 2ヶ月目までに必読。1日1章
- 『**プログラマー脳**』— コードを読む能力の科学的な鍛え方

---

## 第3〜4ヶ月：設計を語れるようになる期間

### やること
1. **設計原則を「使えるレベル」にする**
   - Day 12 の SOLID を、**自分の担当コードで具体例を10個見つける**
   - 「この設計は SRP に反している。なぜなら〜」と言語化する訓練

2. **デザインパターンを実務で使う**
   - まずこの4つだけ：**Strategy**（差し替え）、**Factory**（生成の隠蔽）、**Template Method**（流れの固定）、**Adapter**（既存を繋ぐ）
   - **暗記しない。「今書いているコードがどのパターンに近いか」を探す**

3. **テストを設計の道具として使う**
   - TDD（テストを先に書く）を、小さい機能で試す
   - 「テストが書きにくい＝設計が悪い」を体感する

4. **SQL とデータベースを深める**
   - 実行計画（`EXPLAIN`）を読めるようになる
   - インデックスが効く／効かない条件を理解する
   - トランザクション分離レベル、デッドロックを理解する

5. **レビューする側を経験する**
   - 同期や後輩のPRをレビューする。**教えることが最強の学習法です**

### この期間の目標
- 自分の設計判断を、原則を引用して説明できる
- 遅いクエリを見つけて改善できる
- 他人のPRに理由付きの指摘ができる

### 学習リソース
- 『**現場で役立つシステム設計の原則**』（増田亨）— 日本語で最良の設計入門
- 『**Effective Java 第3版**』— Javaを書く人の必読書。1日1項目
- 『**SQLアンチパターン**』
- 『**テスト駆動開発**』（Kent Beck）

---

## 第5〜6ヶ月：全体を見られるようになる期間

### やること
1. **アーキテクチャの選択肢を知る**
   - レイヤード以外（ヘキサゴナル、クリーンアーキテクチャ、DDD）を学び、**「なぜレイヤードでは足りない場面があるのか」**を理解する
   - ⚠ ただし **現場がレイヤードなら、勝手にDDDを持ち込まないこと**。知識と適用は別です

2. **非機能要件に踏み込む**
   - 性能：JVMのメモリ、GC、プロファイリング（JFR / VisualVM）
   - 可用性：冗長化、ヘルスチェック、グレースフルシャットダウン
   - 運用：監視、アラート設計、ログ設計

3. **インフラの基礎を持つ**
   - Docker、CI/CD、クラウド（AWS or Azure）の基本サービス
   - **「自分の書いたコードがどこでどう動いているか」を知らない開発者は、必ずどこかで詰まります**

4. **設計をリードする経験をする**
   - 小さな機能でよいので、**設計から任せてもらう**
   - 設計レビューで質問攻めにされる経験が、最も成長します

### この期間の目標
- 機能単位の設計を任され、レビューを通せる
- 性能問題を計測して改善できる
- 障害の一次対応ができる

### 学習リソース
- 『**Clean Architecture**』（Robert C. Martin）
- 『**ドメイン駆動設計をはじめよう**』
- 『**Javaパフォーマンス**』
- 『**入門 監視**』

## 書籍を買えない／読む時間がない場合の無料リソース

書籍は最短ルートですが、必須ではありません。以下でも十分に学べます。

| 分野 | 無料リソース |
|---|---|
| Java 全般 | **Oracle 公式 Java チュートリアル**（英語だが最も正確）／ Java API 仕様（javadoc） |
| Spring | **Spring 公式 Guides**（spring.io/guides）— 短いハンズオンが数十本。実務直結 |
| Spring | **Spring 公式リファレンス** — 困ったら必ずここに答えがあります |
| SQL | 各DB製品の公式ドキュメント（PostgreSQL 公式は日本語訳あり） |
| 設計 | 実務のコードそのもの。**OSSのソースを読むのも極めて有効**（Spring 自体が良い教材です） |
| 全般 | **自分が使っているライブラリの GitHub の Issue を読む** — 実際の設計議論が見られます |

> **最強の無料教材は「配属先の既存コード」です。** 実際に稼働していて、実際にお金を生んでいるコードほど良い教材はありません。

## 6ヶ月を通して毎日やること（これが一番効きます）

### 1. 毎日「なぜ」を1つ言語化する
書いたコード、読んだコードについて、**「なぜこうしたのか／こうなっているのか」を1日1つノートに書く**。
これを180日続けると、180個の設計判断の引き出しができます。**これが「設計力」の正体です。**

### 2. 週1で自分のコードを読み返す
1週間前に書いたコードを読み、「今ならこう書く」を考える。**過去の自分は最高の反面教師です。**

### 3. 月1でアウトプットする
社内勉強会、ブログ、チーム内共有 — 形式は何でもよいので、**学んだことを人に説明する**。
説明できない＝理解していない、が明確に分かります。

### 4. 「分からない」を溜めない
その日の疑問はその日のうちに、最低でも「調べるリスト」に書く。**放置した疑問は、半年後に必ず同じ場所で詰まります。**

## やってはいけないこと

| ❌ | なぜダメか |
|---|---|
| 新しい技術を追いかけ続ける | 基礎が固まる前に手を広げると、どれも中途半端になります。**まず今の現場の技術を深く** |
| AIに全部書かせる | 生成されたコードを評価できない人は、AIを使えば使うほど実力が落ちます。**AIには「説明させる」「レビューさせる」** |
| 設計論を振りかざす | 知識で先輩を論破しても、誰も助けてくれなくなります。**現場の制約には必ず理由があります** |
| 動けばいいと考える | 「動く」は最低条件です。**6ヶ月後に読める／直せるコードか**が評価軸になります |
| 質問を我慢する | 悩んだ時間は評価されません。**成果が評価されます** |
| 心身を削る | 一番多い離脱理由は技術力不足ではなく消耗です。**続けられることが最大の才能です** |

## 1年後にいてほしい場所

- **担当システムについては、先輩より詳しい部分がある**
- **設計レビューで、根拠を持って意見を言える**
- **後輩の質問に、理由付きで答えられる**
- **障害が起きたとき、パニックにならず手順を踏める**
- **「この部分はあの人に聞こう」と名前が挙がる**

ここまで来たら、あなたは疑いなく「優秀な開発者」です。
14日間は、その長い道の**最初の一歩を、他の人より深く踏み出す**ためのものでした。

焦らないでください。ただし、止まらないでください。
