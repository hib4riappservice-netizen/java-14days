## ③ 座学（150分）

### なぜデータベースが必要か
Java のプログラムを終了すると、メモリ上のデータは全部消えます。**次に起動しても覚えていてほしいデータ**を置く場所がデータベースです。
ファイル（CSV等）でもできますが、DBには以下の強みがあります。
- **検索が速い**（インデックス）
- **同時に何人がアクセスしても壊れない**（トランザクション・ロック）
- **不正なデータを弾ける**（制約）

### テーブル設計

```sql
CREATE TABLE employees (
    employee_id     VARCHAR(10)  PRIMARY KEY,          -- 主キー（重複不可・NULL不可）
    name            VARCHAR(100) NOT NULL,             -- 必須
    department      VARCHAR(50)  NOT NULL,
    employment_type VARCHAR(20)  NOT NULL,             -- REGULAR / CONTRACT / PART_TIME
    hourly_rate     INTEGER      NOT NULL,
    hired_date      DATE         NOT NULL,             -- 入社日（仕様書 §3.1）
    retired_date    DATE,                              -- NULL なら在職中
    created_at      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE attendances (
    id              BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- 自動採番
    employee_id     VARCHAR(10)  NOT NULL REFERENCES employees(employee_id),  -- 外部キー
    work_date       DATE         NOT NULL,
    clock_in        TIME,
    clock_out       TIME,
    created_at      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (employee_id, work_date)                    -- 1人1日1レコード
);

CREATE INDEX idx_attendances_employee_date ON attendances(employee_id, work_date);
```

**設計のポイント（現場で必ず求められること）**
- **主キー**は必ず設ける。「その行を1つに特定できる列」
- **外部キー**で関連を表す。存在しない社員IDの勤怠が入るのを DB が防いでくれる
- **NOT NULL** を積極的に付ける。「無くてもいい」を許すとバグが増える
- **UNIQUE 制約**で業務ルール（1人1日1件）を DB レベルで守る。**アプリのチェックだけに頼らない**
- **created_at / updated_at** はほぼ全テーブルに付ける（障害調査で必須）
- テーブル名は複数形、カラム名はスネークケース（`employee_id`）が慣習

### 正規化（データの重複をなくす）
悪い設計：
```
attendances(employee_id, employee_name, department, work_date, hours)
```
社員名を勤怠テーブルに持つと、名前が変わったとき **全レコードを更新** しなければならず、更新漏れで矛盾が生じます。

良い設計：社員情報は `employees` テーブルにだけ持ち、勤怠は `employee_id` で参照する。
**「同じ情報を2箇所に持たない」** — これが正規化の本質です。

### SQL 基本
```sql
-- 取得
SELECT employee_id, name FROM employees WHERE department = '営業部';
SELECT * FROM attendances WHERE work_date BETWEEN '2026-08-01' AND '2026-08-31';
SELECT * FROM employees ORDER BY name ASC LIMIT 10;

-- 追加（NOT NULL の列は全部書く。hired_date を忘れると not-null constraint 違反になります）
INSERT INTO employees (employee_id, name, department, employment_type, hourly_rate, hired_date)
VALUES ('E001', '田中太郎', '営業部', 'REGULAR', 2000, DATE '2020-04-01');

-- 更新（⚠ WHERE を忘れると全件更新される。実際の重大事故が多数）
UPDATE employees SET department = '開発部' WHERE employee_id = 'E001';

-- 削除
DELETE FROM attendances WHERE work_date < '2020-01-01';
```

> **【現場の鉄則】UPDATE / DELETE は、必ず先に同じ WHERE で SELECT して件数を確認してから実行する。**
> `WHERE` を書き忘れて全社員のデータを消した、という事故は毎年どこかで起きています。

### JOIN（複数テーブルを繋ぐ）
```sql
SELECT e.name, a.work_date, a.clock_in, a.clock_out
FROM attendances a
INNER JOIN employees e ON a.employee_id = e.employee_id
WHERE a.work_date >= '2026-08-01';
```
- **INNER JOIN**：両方に存在するものだけ
- **LEFT JOIN**：左（FROM側）は全部、右は無ければ NULL

### 集計
```sql
SELECT
    e.name,
    COUNT(*)                                                          AS work_days,
    SUM(EXTRACT(EPOCH FROM (a.clock_out - a.clock_in)) / 3600)        AS total_hours
FROM attendances a
JOIN employees e ON a.employee_id = e.employee_id
WHERE a.work_date BETWEEN '2026-08-01' AND '2026-08-31'
GROUP BY e.employee_id, e.name
HAVING COUNT(*) > 15
ORDER BY total_hours DESC;
```
- `GROUP BY` でグループ化、`SUM`/`COUNT`/`AVG`/`MAX` で集計
- `WHERE` は集計**前**の絞り込み、`HAVING` は集計**後**の絞り込み

> **【重要】SQLには「方言」があります。**
> 標準SQL（SELECT / WHERE / JOIN / GROUP BY など）はどのDBでも同じですが、**日時計算・文字列関数・自動採番の書き方はDB製品ごとに違います。**
> 上の例は **PostgreSQL の書き方**です（本教材は Day 8〜14 すべて PostgreSQL で進めます）。他製品では同じ計算がこうなります。
> ```sql
> -- MySQL の場合
> SUM(TIMESTAMPDIFF(MINUTE, a.clock_in, a.clock_out)) / 60.0 AS total_hours
> -- H2 / SQL Server の場合
> SUM(DATEDIFF('MINUTE', a.clock_in, a.clock_out)) / 60.0    AS total_hours
> ```
> **現場での教訓：「動かないSQL」の原因の多くは方言違いです。** エラーが出たら、まず「このDB製品ではこの関数は存在するか」を確認してください。
> **とくに危険なのが「開発は H2、本番は PostgreSQL」という構成**です。手元では通ったSQLが本番で落ちます。**本教材が最初から本番と同じ PostgreSQL を使うのは、この事故を体験させないため**です。
> なお **JPA（Day 10）を使うと、この方言差はフレームワークがある程度吸収してくれます。** これがORMを使う実利的な理由の1つです（ただしネイティブSQLを書けば方言は残ります）。

### トランザクション
```sql
BEGIN;
  UPDATE accounts SET balance = balance - 10000 WHERE id = 1;   -- 引き落とし
  UPDATE accounts SET balance = balance + 10000 WHERE id = 2;   -- 入金
COMMIT;   -- 両方成功したら確定
-- 途中で失敗したら ROLLBACK して両方なかったことにする
```
**「引き落としだけ成功して入金が失敗」を絶対に起こさない仕組み**です。これが無いと業務システムは成立しません。

### インデックス
検索対象の列に索引を作ると検索が劇的に速くなります。ただし：
- **書き込みは遅くなる**（索引も更新するため）
- **付けすぎは害**。WHERE や JOIN でよく使う列に絞る

### 【重要】SQLインジェクション
```java
// ❌❌❌ 絶対にやってはいけない
String sql = "SELECT * FROM employees WHERE employee_id = '" + userInput + "'";
```
`userInput` に `' OR '1'='1` と入れられると、全件が返ります。`'; DROP TABLE employees; --` なら**テーブルが消えます**。

```java
// ⭕ 正しい：プレースホルダを使う
String sql = "SELECT * FROM employees WHERE employee_id = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, userInput);
```
**「SQLを文字列連結で組み立てない」は絶対ルールです。** これは実際に企業が個人情報を大量流出させている、最も有名な脆弱性です。

### N+1問題（性能問題の最頻出パターン）
```java
List<Employee> employees = repository.findAll();          // 1回のクエリ
for (Employee e : employees) {
    List<Attendance> list = attendanceRepo.findByEmployeeId(e.getId());  // N回のクエリ！
}
```
社員1000人なら **1001回** クエリが飛び、システムが停止レベルで遅くなります。
**対策**：JOIN で1回にまとめる、または `IN` 句でまとめて取得する。
**この問題を知っているかどうかは、面接でもレビューでも問われます。**

## ③ 座学（150分）

### HTTPとは
ブラウザ（クライアント）とサーバの会話ルールです。

```
【リクエスト】クライアント → サーバ
GET /api/employees/E001 HTTP/1.1
Host: example.com
Accept: application/json

【レスポンス】サーバ → クライアント
HTTP/1.1 200 OK
Content-Type: application/json

{"employeeId":"E001","name":"田中太郎","department":"営業部"}
```

### HTTPメソッドとステータスコード

| メソッド | 意味 | 例 |
|---|---|---|
| GET | 取得（何も変えない） | `GET /api/employees` |
| POST | 新規作成 | `POST /api/attendances` |
| PUT | 全体を置き換え | `PUT /api/employees/E001` |
| PATCH | 一部だけ更新 | `PATCH /api/employees/E001` |
| DELETE | 削除 | `DELETE /api/attendances/1` |

| コード | 意味 | いつ返すか |
|---|---|---|
| 200 OK | 成功 | GET/PUT の成功 |
| 201 Created | 作成成功 | POST の成功 |
| 204 No Content | 成功・返す内容なし | DELETE の成功 |
| 400 Bad Request | リクエストが不正 | バリデーションエラー |
| 401 Unauthorized | 未認証 | ログインしていない |
| 403 Forbidden | 権限なし | ログイン済だが権限不足 |
| 404 Not Found | 見つからない | 存在しないIDを指定 |
| 409 Conflict | 競合 | 重複登録 |
| 500 Internal Server Error | サーバ側の異常 | 想定外の例外 |

> **【重要】404 と 500 の使い分け。** 「社員が見つからない」は**クライアントが悪い**ので 404。「DBに繋がらない」は**サーバが悪い**ので 500。
> **エラーを全部 500 で返すAPIは、現場で必ず指摘されます。** クライアント側が「自分が悪いのかサーバが落ちているのか」判断できないからです。

### RESTの考え方
- **URLは「モノ（リソース）」を表す名詞にする**。動詞を入れない
  - ⭕ `GET /api/employees/E001`
  - ❌ `GET /api/getEmployee?id=E001`
- **操作はHTTPメソッドで表す**
- 階層構造で関連を表す：`GET /api/employees/E001/attendances`

### Spring Boot：最小のAPI

**プロジェクト作成**：https://start.spring.io で以下を選択
- Project: **Maven** / Language: **Java**
- Spring Boot: **4.1.x（既定で選択されているもの）**
- Java: **21** ← **⚠ 既定は 17 です。必ず 21 に変更してください**（本教材は Java 21 前提）
- Group: `com.example` / Artifact: **`attendance-api`** / Package name: `com.example.attendance`
- Dependencies: **`Spring Web`** と **`Validation`** の**2つだけ**

生成された Zip を展開し、**リポジトリ内の `attendance-api/` に配置**してコミットしてください。

> **⚠ 今日は `Spring Data JPA` と `PostgreSQL Driver` を入れません。** 入れると Spring Boot が起動時にDB接続先を探しに行き、設定が無いために
> `Failed to configure a DataSource: 'url' attribute is not specified` で**起動に失敗します**。
> 今日はデータをメモリ上の `Map` で持つので、DBは不要です。**DB関連の依存は Day 10 で追加します**（`pom.xml` に後から書き足すだけです）。
> これは「依存を入れた瞬間に Spring が自動設定を始める」という**Spring Boot の性質そのもの**です。便利さの裏返しで、**使わない依存を入れると起動しなくなる**——現場でも新規プロジェクト作成時によく踏みます。
>
> **Lombok も今日は使いません。** 実務では多用されますが、**まず自分の手でゲッターとコンストラクタを書き、何が自動生成されるのかを知ってから**導入します（Day 10 で入れます）。

```java
// 起動クラス（自動生成される）
@SpringBootApplication
public class AttendanceApplication {
    public static void main(String[] args) {
        SpringApplication.run(AttendanceApplication.class, args);
    }
}
```

```java
// 最小のController
@RestController                       // 「これはHTTPを受け付けるクラスです」
@RequestMapping("/api/employees")     // このクラスの共通URL
public class EmployeeController {

    @GetMapping("/{id}")              // GET /api/employees/E001
    public EmployeeResponse findById(@PathVariable String id) {
        return new EmployeeResponse(id, "田中太郎", "営業部");
    }
}

public record EmployeeResponse(String employeeId, String name, String department) {}
```

起動して `http://localhost:8080/api/employees/E001` を開くと、**JSONが返ります**。
`record` が自動的にJSONに変換されます（Jackson というライブラリが裏でやっています）。

### 【最重要】DI（依存性の注入）とは何か

これがSpringの核心であり、**Day 4 のインタフェースが「何のためにあったか」の答え**です。

**DI無しで書くとこうなります（悪い）**
```java
public class EmployeeService {
    private EmployeeRepository repository = new JdbcEmployeeRepository();  // 自分で作っている
}
```

**何が問題か**
1. **テストできない**。テスト時に本物のDBに繋ぎに行ってしまう
2. **差し替えられない**。JDBC から JPA に変えたい時、このクラスを修正する必要がある
3. **管理できない**。DB接続を100箇所で `new` すると、接続が100個作られてDBがパンクする

**DI ありだとこうなります（良い）**
```java
@Service                                          // 「Springが管理する部品です」
public class EmployeeService {

    private final EmployeeRepository repository;  // インタフェース型で持つ

    // コンストラクタで外から受け取る ← これが「注入」
    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }

    public Employee findById(String id) {
        return repository.findById(id)
            .orElseThrow(() -> new EmployeeNotFoundException(id));
    }
}
```

**Springがやってくれること**：起動時に `@Service` `@Repository` `@RestController` が付いたクラスを全部見つけて**インスタンスを1個ずつ作り**（これを **Bean** と呼びます）、必要な場所に**自動で渡します**。

これで：
1. **テストで偽物（モック）に差し替えられる** → 高速で安定したテストが書ける
2. **実装を変えても Service は無修正**
3. **インスタンスは1個だけ**なので資源が無駄にならない

> **「制御の反転（IoC）」の意味**：あなたが `new` する（あなたが制御する）のではなく、**フレームワークが作ってあなたに渡す**（フレームワークが制御する）。これが「反転」です。

### DIの書き方：コンストラクタインジェクション一択
```java
// ⭕ 推奨：コンストラクタインジェクション
@Service
public class EmployeeService {
    private final EmployeeRepository repository;
    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }
}

// ❌ 非推奨：フィールドインジェクション
@Service
public class EmployeeService {
    @Autowired
    private EmployeeRepository repository;   // final にできない、テストしにくい
}
```
**理由**：コンストラクタ方式なら `final` にできて不変になり、テスト時に `new EmployeeService(mockRepo)` と普通に書けます。**現場では @Autowired フィールドインジェクションはレビューで指摘対象**です。

> **なお、コンストラクタが1つだけのクラスでは `@Autowired` は省略できます**（Spring 4.3以降）。上の例のように何も付けないのが現在の標準です。
> 実務では Lombok の `@RequiredArgsConstructor` でコンストラクタを自動生成します。**本教材でも Day 10 で導入しますが、今日は手で書いてください。** 自動生成される中身を知らずに使うと、事故の原因を追えなくなります。

## ② 新出用語
レイヤードアーキテクチャ / Controller / Service / Repository / Entity / DTO / @Entity / @Id / JpaRepository / @Transactional / マッピング / 単方向依存 / @ManyToOne / 遅延ロード / Flyway / マイグレーション / Lombok

## ③ 座学（180分）

### レイヤードアーキテクチャ

```
HTTPリクエスト
    ↓
■ Controller層 ―「受付」
    ・HTTPを受け取り、Serviceを呼び、結果を返す
    ・業務ロジックは書かない
    ・DTO(Request/Response)を扱う
    ↓ 呼ぶ
■ Service層 ―「頭脳」
    ・業務ルールを書く（アプリの心臓部）
    ・トランザクション境界
    ・HTTPのことも SQL のことも知らない
    ↓ 呼ぶ
■ Repository層 ―「倉庫番」
    ・DBへの読み書きだけ
    ・業務ルールは書かない
    ・Entityを扱う
    ↓
データベース
```

**絶対のルール：依存は上から下への一方向のみ。**
- Controller → Service → Repository ⭕
- Repository → Service ❌（絶対に呼ばない）
- Controller → Repository ❌（Serviceを飛ばさない）

**なぜ層を分けるのか（これを説明できることが重要です）**
1. **変更の影響を閉じ込められる**。DBを PostgreSQL から Oracle に変えても、修正は Repository 層だけ。Service は無傷
2. **テストしやすい**。Service のテストで DB を使わずに済む（Repository をモック化）
3. **役割が明確で、複数人で分担できる**
4. **どこに何を書くか迷わない**。「これは業務ルールだから Service」と即断できる

### Entity と DTO を分ける理由（現場で最重要の設計判断の1つ）

```java
// Entity：DBのテーブルに対応
@Entity
@Table(name = "employees")
public class EmployeeEntity {
    @Id
    private String employeeId;
    private String name;
    private String department;
    private Integer hourlyRate;      // 給与情報
    private String passwordHash;     // 認証情報
    // ...
}

// DTO（Response）：APIで外に返すもの
public record EmployeeResponse(String employeeId, String name, String department) {}
```

**Entity をそのまま API のレスポンスにしてはいけない理由**
1. **情報漏洩**。`passwordHash` や `hourlyRate` まで外部に返ってしまいます。**これは実際のセキュリティ事故の典型です**
2. **DBの都合がAPI仕様に漏れる**。カラム名を変えたらAPIの項目名まで変わり、利用者が壊れる
3. **JPAの遅延読み込み**が絡んで意図しないSQLが飛ぶ

**現場のルール：層をまたぐデータは必ず変換する。** これは面倒に見えますが、必ず守ってください。

### JPA でのDB連携

**まず依存を追加します**（Day 9 では入れていません）。`attendance-api/pom.xml` に以下を追加し、IntelliJ 右端の Maven パネルで🔄を押してください。
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>

</dependency>
```

> **【Spring Boot 4 の重要な作法】`spring-boot-starter-xxx` を足したら、`spring-boot-starter-xxx-test`（testスコープ）も対で足します。**
> Boot 4 でフレームワークが細かいモジュールに分割され、**テスト用のアノテーションが本体の starter から切り離された**ためです。
> これを忘れると、Day 13 で `@DataJpaTest` を書いたときに「シンボルが見つかりません」となります。**エラーの原因が「テストの書き方」ではなく「依存の入れ忘れ」なので、非常に気づきにくい**箇所です。
>
> 同じ理由で、Day 9 で入れた Web の分も対にしておきます。
> ```xml
> <dependency>
>     <groupId>org.springframework.boot</groupId>
>     <artifactId>spring-boot-starter-webmvc-test</artifactId>
>     <scope>test</scope>      <!-- @WebMvcTest / @AutoConfigureMockMvc はこちら -->
> </dependency>
> ```

**この時点でアプリは起動しなくなります**（接続先が未設定のため）。この節の最後にある `application.yml` を書けば起動します。**「依存を足す → 設定を書く」はセット**だと覚えてください。

```java
// Entity
@Entity
@Table(name = "employees")
public class EmployeeEntity {

    @Id
    @Column(name = "employee_id")
    private String employeeId;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false)
    private String department;

    @Enumerated(EnumType.STRING)          // enumを文字列でDBに保存
    @Column(name = "employment_type", nullable = false)
    private EmploymentType employmentType;

    @Column(name = "hourly_rate", nullable = false)
    private Integer hourlyRate;

    @Column(name = "hired_date", nullable = false)
    private LocalDate hiredDate;

    // NULL 許容（在職中は null）なのでコンストラクタ引数には含めない。Day 11 の BR-04 で使う
    @Column(name = "retired_date")
    private LocalDate retiredDate;

    @Column(name = "created_at", nullable = false)
    private LocalDateTime createdAt;

    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;

    protected EmployeeEntity() {}          // JPAが要求する引数なしコンストラクタ【暗記でOK】

    // ⚠ NOT NULL の列は「全部」コンストラクタで受け取ること。
    //    1つでも漏らすと保存時に PropertyValueException / DataIntegrityViolationException になります
    public EmployeeEntity(String employeeId, String name, String department,
                          EmploymentType employmentType, Integer hourlyRate, LocalDate hiredDate) {
        this.employeeId = employeeId;
        this.name = name;
        this.department = department;
        this.employmentType = employmentType;
        this.hourlyRate = hourlyRate;
        this.hiredDate = hiredDate;
    }

    /** 保存直前にJPAが呼ぶ。登録日時のような「DBに入る瞬間に決まる値」はここで入れる */
    @PrePersist
    void onCreate() {
        this.createdAt = LocalDateTime.now();   // ⚠ Day 13 で Clock 注入に直します
        this.updatedAt = this.createdAt;
    }

    /** 更新直前にJPAが呼ぶ。EMP-04（更新）や EMP-05（退職）で自動的に更新される */
    @PreUpdate
    void onUpdate() {
        this.updatedAt = LocalDateTime.now();
    }

    /** 部署異動（EMP-04 で使う。@Setter は付けず、業務名のメソッドで変更する） */
    public void changeDepartment(String newDepartment) {
        this.department = newDepartment;
    }

    /** 時給改定（EMP-04 で使う） */
    public void changeHourlyRate(Integer newHourlyRate) {
        this.hourlyRate = newHourlyRate;
    }

    /** 退職する（Day 11 の EMP-05 で使う業務イベント。setter は作らない） */
    public void retire(LocalDate retiredDate) {
        if (this.retiredDate != null) {
            // ⚠ IllegalStateException にしないこと。それだと 500 になります（下の注記）
            throw new AlreadyRetiredException(employeeId);
        }
        this.retiredDate = retiredDate;
    }

    public boolean isRetired() {
        return retiredDate != null;
    }
    // ゲッター群...
}
```

> **【重要】業務ルール違反に `IllegalStateException` や `IllegalArgumentException` を使わないでください。**
> Java標準の例外は「プログラムのバグ」を表すもので、Day 11 の `GlobalExceptionHandler` では拾い漏らして **500（サーバの異常）** になります。
> 「すでに退職済み」は**利用者の操作が原因**なので、正しくは **409 Conflict** です。**専用のカスタム例外を作り、409 に対応付けます**。
> ```java
> public class AlreadyRetiredException extends RuntimeException {
>     public AlreadyRetiredException(String employeeId) {
>         super("すでに退職済みです: " + employeeId);
>     }
> }
> ```
> **「例外の種類 ＝ HTTPステータス」を設計として対応付ける**のが Day 11 の主題です。標準例外を投げた時点で、その対応付けができなくなります。

> **`@PrePersist` を使う理由**：`createdAt` をコンストラクタで入れると、「まだ保存していないオブジェクト」にも作成日時が入ってしまい、意味がずれます。**「DBに入った時刻」はDBに入る直前に決めるのが正しい**です。
> なお `LocalDateTime.now()` の直接呼び出しは**テストで時刻を固定できない**ため、Day 13 で `Clock` 注入に直します。**今は「あとで直す前提の暫定コード」だと認識しておいてください。**

### テーブル同士の関連（`@ManyToOne`）
勤怠は「1人の社員に複数件」ぶら下がります。この関係を Entity で表すのが `@ManyToOne` です。

```java
@Entity
@Table(name = "attendances")
public class AttendanceEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // DBの自動採番に任せる
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)          // 多(勤怠) 対 一(社員)
    @JoinColumn(name = "employee_id", nullable = false)   // 外部キーのカラム名
    private EmployeeEntity employee;

    @Column(name = "work_date", nullable = false)
    private LocalDate workDate;

    @Column(name = "clock_in")
    private LocalTime clockIn;

    @Column(name = "clock_out")
    private LocalTime clockOut;

    protected AttendanceEntity() {}

    // 社員は「オブジェクトごと」渡す（employeeId という文字列は持たせない）
    public AttendanceEntity(EmployeeEntity employee, LocalDate workDate,
                            LocalTime clockIn, LocalTime clockOut) {
        this.employee = employee;
        this.workDate = workDate;
        this.clockIn = clockIn;
        this.clockOut = clockOut;      // 打刻漏れは null を許容する（仕様書 §3.2）
    }
    // ゲッター群...
}
```

- **`fetch = FetchType.LAZY` を必ず指定してください。** 既定の `EAGER` は「勤怠を1件取るたびに社員も自動で取りに行く」動きになり、**N+1問題の主要因**になります
- LAZY にすると `attendance.getEmployee().getName()` を呼んだ瞬間に追加のSQLが飛びます。**まとめて取りたいときは下の課題4の `JOIN FETCH`** を使います
- 逆向き（社員 → 勤怠一覧）の `@OneToMany` は、**必要になるまで書かないでください**。双方向にすると無限ループ（`toString`／JSON変換）や意図しないSQLの温床になります

> **【重要】関連を持つと、クエリメソッドの名前の付け方が変わります。**
> `AttendanceEntity` が持つのは `employeeId`（文字列）ではなく `employee`（オブジェクト）です。そのため以下は**動きません**。
> ```java
> // ❌ 起動時に PropertyReferenceException: No property 'employeeId' found
> List<AttendanceEntity> findByEmployeeIdAndWorkDateBetween(String id, LocalDate from, LocalDate to);
> ```
> **関連の先をたどるときは `_`（アンダースコア）で区切ります。**
> ```java
> // ⭕ 「employee の employeeId」をたどる
> List<AttendanceEntity> findByEmployee_EmployeeIdAndWorkDateBetween(
>         String employeeId, LocalDate from, LocalDate to);
> ```
> **これはコンパイルエラーではなく、アプリ起動時のエラーとして出ます。** Spring Data はメソッド名を解析してSQLを組み立てるため、名前の間違いは実行するまで分かりません。**「クエリメソッドを書いたら、すぐ起動して確かめる」** のが実務の作法です。

```java
// Repository：インタフェースを書くだけで実装はSpringが作る
public interface EmployeeRepository extends JpaRepository<EmployeeEntity, String> {

    // メソッド名から自動でSQLが生成される（クエリメソッド）
    List<EmployeeEntity> findByDepartment(String department);
    Optional<EmployeeEntity> findByEmployeeId(String employeeId);
    List<EmployeeEntity> findByDepartmentAndEmploymentType(String dept, EmploymentType type);

    // 複雑なものは自分でJPQLを書く
    @Query("SELECT e FROM EmployeeEntity e WHERE e.hourlyRate > :rate ORDER BY e.name")
    List<EmployeeEntity> findHighRateEmployees(@Param("rate") int rate);
}
```
`JpaRepository` を継承するだけで、`save()` `findById()` `findAll()` `delete()` が使えます。
（主キーが `employeeId` なので、`findByEmployeeId` は `findById` と同じものです。**継承で手に入るメソッドを自分で書き足さない**よう注意してください）

勤怠側は、関連をたどるので `_` 区切りになります。
```java
public interface AttendanceRepository extends JpaRepository<AttendanceEntity, Long> {

    List<AttendanceEntity> findByEmployee_EmployeeIdAndWorkDateBetween(
            String employeeId, LocalDate from, LocalDate to);

    boolean existsByEmployee_EmployeeIdAndWorkDate(String employeeId, LocalDate workDate);  // BR-01 の重複チェック用
}
```

```java
// Service
@Service
@Transactional(readOnly = true)     // 読み取り専用トランザクション（性能が良い）
public class EmployeeService {

    private final EmployeeRepository repository;

    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }

    public EmployeeResponse findById(String employeeId) {
        EmployeeEntity entity = repository.findById(employeeId)
            .orElseThrow(() -> new EmployeeNotFoundException(employeeId));
        return toResponse(entity);              // Entity → DTO 変換
    }

    // ⚠ Day 9 では EmployeeCreateRequest(name, department) の2項目でしたが、
    //    ここからは 05_project-spec.md §3.1 の社員項目に合わせて
    //    (employeeId, name, department, employmentType, hourlyRate, hiredDate) に拡張します
    @Transactional                              // 書き込みがあるのでこちらを上書き指定
    public EmployeeResponse create(EmployeeCreateRequest request) {
        if (repository.existsById(request.employeeId())) {
            throw new DuplicateEmployeeException(request.employeeId());
        }
        EmployeeEntity entity = new EmployeeEntity(
            request.employeeId(), request.name(), request.department(),
            request.employmentType(), request.hourlyRate(), request.hiredDate());
        EmployeeEntity saved = repository.save(entity);
        return toResponse(saved);
    }

    private EmployeeResponse toResponse(EmployeeEntity e) {
        return new EmployeeResponse(e.getEmployeeId(), e.getName(), e.getDepartment());
    }
}
```

### 【実務標準】Lombok で定型コードを消す

ここまでで気づいたと思いますが、**Entity のゲッターとコンストラクタを手で書くのは苦痛**です。現場の Spring Boot プロジェクトでは、ほぼ確実に **Lombok** が使われています。

> **⚠ Day 9 までは意図的に手で書かせました。** 「Lombok が何を生成しているか」を知らずに使うと、`@Data` を Entity に付けて無限ループやパフォーマンス事故を起こします。**手で書ける人が、書かなくて済ませるために使う**のが正しい順序です。

**導入**（`attendance-api/pom.xml`）
```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>
```
IntelliJ 側で **Settings → Build, Execution, Deployment → Compiler → Annotation Processors → 「Enable annotation processing」をON**にしてください（**これを忘れると「シンボルが見つかりません」の嵐になります**。最頻出のつまずきです）。

**Service：コンストラクタを自動生成**
```java
@Service
@RequiredArgsConstructor          // final フィールドを引数に取るコンストラクタを生成
@Transactional(readOnly = true)
public class EmployeeService {

    private final EmployeeRepository repository;   // これだけで注入される
}
```
（フィールドを増やせば、そのぶんコンストラクタの引数も自動で増えます。**Day 13 で `Clock` を足すときも、この行に1行足すだけ**です）

**Entity：使ってよいものと、使ってはいけないもの**
```java
@Entity
@Table(name = "employees")
@Getter                                   // ⭕ ゲッターだけ生成
@NoArgsConstructor(access = AccessLevel.PROTECTED)   // ⭕ JPAが要求する引数なしコンストラクタ
public class EmployeeEntity {
    // ...
}
```

| アノテーション | Entity での可否 | 理由 |
|---|---|---|
| `@Getter` | ⭕ | 安全 |
| `@NoArgsConstructor(access = PROTECTED)` | ⭕ | JPA の要求を満たしつつ、外部からの生成を防げる |
| `@Setter` | ❌ | 全項目が変更可能になり、**カプセル化が壊れる**（Day 3 で学んだ通り） |
| `@Data` | ❌❌ | `@Setter` に加えて `equals`/`hashCode`/`toString` を全項目で生成。**関連（`@ManyToOne`）を持つ Entity では、`toString` が相手を呼び、相手が自分を呼んで無限ループ／意図しないSQL大量発行**を起こします |
| `@AllArgsConstructor` | △ | 引数の順番を間違えても**同じ型なら気づけない**。項目が多い Entity では明示的なコンストラクタの方が安全 |

> **`@Data` を Entity に付けるのは、現場のレビューで確実に指摘される典型的なアンチパターンです。** 「便利だから全部付ける」ではなく、**1つずつ理由を言えるものだけ付ける**。これが Lombok との正しい付き合い方です。
>
> **DTO は `record` で書けば Lombok すら不要**です（Java 16以降）。**新しく書くDTOは record が第一選択**、Lombok は Entity と Service の定型削減に使う、という住み分けが現在の実務です。

### @Transactional の意味
このアノテーションが付いたメソッドは、**開始時にトランザクションが始まり、正常終了で COMMIT、例外が出たら自動 ROLLBACK** されます。

```java
@Transactional
public void registerMonthlyAttendance(String employeeId, List<AttendanceRequest> list) {
    for (AttendanceRequest r : list) {
        attendanceRepository.save(toEntity(employeeId, r));
    }
    summaryRepository.save(calculateSummary(employeeId, list));
    // ここで例外が出たら、上で保存したもの全部が取り消される
}
```

**現場のルール**
- **トランザクション境界は Service に置く**（Controller や Repository ではない）
- **読み取りだけのメソッドには `@Transactional(readOnly = true)`**（DBが最適化してくれる）
- **⚠ 同じクラス内のメソッドを自分で呼んでも @Transactional は効きません**（Springがプロキシという仕組みで介入するため、内部呼び出しは素通りします）。これは非常に有名なハマりどころです

> **`ddl-auto` は本教材では最初から `validate` で通します。**
>
> | 値 | 動き | 使ってよい場面 |

> | `validate` | Entity とテーブルが一致しているか検証するだけ | **本教材はこれ。本番もこれ** |

### 【実務標準】Flyway でスキーマを管理する

**現場では、テーブルの作成・変更を手作業でも `ddl-auto` でも行いません。** `V1__init.sql` のような**連番付きのSQLファイルをリポジトリに置き、アプリ起動時に未適用のものだけを自動で流す**仕組みを使います。これがマイグレーションツール（Flyway / Liquibase）です。

**なぜ必要か（これは面接でも聞かれます）**
1. **本番・検証・各開発者のDBを、確実に同じ状態にできる**。「あの人のPCにだけ列が無い」が起きない
2. **変更履歴が Git に残る**。「この列はいつ、なぜ追加されたか」を追える
3. **適用済みかどうかを Flyway が記録する**（`flyway_schema_history` テーブル）。二重適用も適用漏れも起きない
4. **リリース手順が「アプリをデプロイする」だけになる**。深夜に手作業でSQLを流す運用から解放される

### クエリパラメータ・パス変数の検証（`@RequestBody` だけでは足りない）

`?year=2026&month=13` のような**URLに乗ってくる値**は、`@Valid @RequestBody` では検証されません。**引数に直接、制約アノテーションを付けます。**

```java
@RestController
@RequestMapping("/api/employees")
// ⚠ クラスに @Validated は付けないこと（理由は下の注記）
public class EmployeeController {

    @GetMapping("/{id}/summary")
    public MonthlySummaryResponse summary(
            @PathVariable String id,
            @RequestParam @Min(2000) @Max(2100) int year,
            @RequestParam @Min(1) @Max(12) int month) {
        return summaryService.summarize(id, year, month);
    }
}
```

| 検証したい場所 | 必要なもの | 違反時に飛ぶ例外 |
|---|---|---|
| `@RequestBody`（JSON本体） | 引数に **`@Valid`** | `MethodArgumentNotValidException` |
| `@RequestParam` / `@PathVariable` | **引数に制約アノテーションを付けるだけ** | `HandlerMethodValidationException` |

> **【重要・古い記事に注意】ネット上には「クラスに `@Validated` を付けろ」という記事が大量にありますが、それは Spring Framework 6.0 以前の話です。**
> **Spring Framework 6.1（Spring Boot 3.2）以降、Spring MVC はメソッド引数の検証を組み込みで行うようになりました。** そのため `@Validated` は不要です。
> **それどころか、クラスに `@Validated` を付けると有害です。** AOPプロキシ経由の古い検証が優先され、組み込みの検証が働かなくなり、飛ぶ例外が `HandlerMethodValidationException` ではなく **`ConstraintViolationException`** に変わります。下の `GlobalExceptionHandler` で拾い漏らすと **400 のはずが 500 になります**。
> Spring 公式リファレンスも「6.1 の組み込みメソッド検証を活かすには、コントローラからクラスレベルの `@Validated` を外す必要がある」と明記しています。
>
> **確認方法**：`?month=13` を実際に叩いて **400 が返ることを目で見る**。**500 が返ったら、まずクラスに `@Validated` が付いていないか疑ってください。**

### バリデーションの2段構え（これが実務の設計）
| 層 | 何をチェックするか | 例 |
|---|---|---|
| **Controller（形式チェック）** | 形が正しいか。単体で判断できること | 必須、桁数、形式、範囲 |
| **Service（業務チェック）** | 業務ルール上OKか。DBを見ないと分からないこと | 社員IDの重複、退職済み社員への打刻、同日二重打刻 |

**「重複していないか」は Controller ではチェックできません（DBを見る必要があるため）。** 責務の分け方として重要です。

### 統一エラーレスポンス
バラバラなエラー形式は、API利用者を困らせます。全体で1つに統一します。

```java
public record ErrorResponse(
    String code,               // アプリ独自のエラーコード
    String message,            // 利用者向けメッセージ
    List<FieldError> errors,   // 項目別エラー（バリデーション時）
    String traceId             // 問い合わせ時に使う追跡ID
) {
    public record FieldError(String field, String message) {}
}
```

```java
@RestControllerAdvice     // 全Controllerの例外をここで一括処理する
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // バリデーションエラー → 400
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        List<ErrorResponse.FieldError> errors = e.getBindingResult().getFieldErrors().stream()
            .map(fe -> new ErrorResponse.FieldError(fe.getField(), fe.getDefaultMessage()))
            .toList();
        log.warn("入力値エラー: {}", errors);
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_ERROR", "入力内容を確認してください",
                                    errors, MDC.get("traceId")));
    }

    // 業務例外：見つからない → 404
    @ExceptionHandler(EmployeeNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(EmployeeNotFoundException e) {
        log.warn("該当データなし: {}", e.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse("EMPLOYEE_NOT_FOUND", e.getMessage(),
                                    List.of(), MDC.get("traceId")));
    }

    // 業務例外：競合 → 409（重複登録・二重打刻・二重退職など）
    @ExceptionHandler({DuplicateEmployeeException.class,
                       DuplicateAttendanceException.class,
                       AlreadyRetiredException.class})
    public ResponseEntity<ErrorResponse> handleConflict(RuntimeException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ErrorResponse("CONFLICT", e.getMessage(),
                                    List.of(), MDC.get("traceId")));
    }

    // ⚠ 以下は「クライアントが悪い」ので必ず400。個別に書かないと、下の handleUnexpected に
    //    吸い込まれて500になります（＝Day 9 で「やってはいけない」と学んだ状態）
    @ExceptionHandler({
        HandlerMethodValidationException.class,      // ?month=13 など（クエリ/パス変数の制約違反）
        ConstraintViolationException.class,          // 同上。クラスに @Validated を付けた場合はこちらが飛ぶ
        MethodArgumentTypeMismatchException.class,   // ?month=abc など（型変換に失敗）
        HttpMessageNotReadableException.class        // 壊れたJSON、必須のリクエストボディが空
    })
    public ResponseEntity<ErrorResponse> handleBadRequest(Exception e) {
        log.warn("不正なリクエスト: {}", e.getMessage());
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("BAD_REQUEST", "リクエストの形式を確認してください",
                                    List.of(), MDC.get("traceId")));
    }

    // 存在しないURLへのアクセスは 404（これが無いと下の handleUnexpected が拾って500になります）
    @ExceptionHandler(NoResourceFoundException.class)
    public ResponseEntity<ErrorResponse> handleNoResource(NoResourceFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse("NOT_FOUND", "指定されたURLは存在しません",
                                    List.of(), MDC.get("traceId")));
    }

    // 想定外 → 500
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
        log.error("想定外のエラーが発生しました", e);      // ← ここは必ず error レベル＋例外を渡す
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ErrorResponse("INTERNAL_ERROR",
                  "システムエラーが発生しました。時間をおいて再度お試しください",
                  List.of(), MDC.get("traceId")));
    }
}
```

> **`@ExceptionHandler(Exception.class)` を1つ置くと、書き忘れた例外が全部500になります。**
> Spring はより具体的なハンドラを優先するので、**400・404 で返すべきものを1つずつ明示的に書き出す**必要があります。
> **特に見落とすのが `NoResourceFoundException`（存在しないURL）です。** これを書かないと、URLを打ち間違えただけで 500 が返る API になります。「エラーを全部500で返すAPIは現場で必ず指摘される」（Day 9）の、最も踏みやすい実例です。
> **「壊れたJSONを送ったら500が返るAPI」は、利用者が自分の誤りに気づけません。** Day 9 で学んだ「404と500の使い分け」と同じ話です。
> **確認方法**：`curl` で `{"employeeId":` のような壊れたJSONを送り、**400 が返ることを確かめてください。**

> **【セキュリティ上の必須事項】500エラーのレスポンスに、例外メッセージやスタックトレースをそのまま入れてはいけません。**
> DBのテーブル名や内部構造が攻撃者に漏れます。**詳細はログに、利用者には一般的なメッセージと traceId を返す** — これが正解です。
> traceId があれば、問い合わせを受けたときログから該当処理を一発で特定できます。

### トレースID（障害調査の生命線）
```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = UUID.randomUUID().toString().substring(0, 8);
        MDC.put("traceId", traceId);           // MDC = ログに自動で付与される情報の置き場
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                        // ⚠ 必ずクリアする（スレッド使い回しのため）
        }
    }
}
```
logback設定で `[%X{traceId}]` を出力形式に入れると、**全ログ行に自動で traceId が付きます**。「1リクエストの処理を全部追える」ようになり、障害調査の時間が劇的に減ります。

### SOLID原則（1つずつコードで理解する）

#### S：単一責任の原則（SRP）— 最も重要
**「1つのクラスは、1つの理由でだけ変更されるべき」**

```java
// ❌ 悪い：3つの責務が混在
public class AttendanceService {
    public void register(Attendance a) {
        // ① 業務ロジック
        if (a.getClockOut().isBefore(a.getClockIn())) { throw ...; }
        // ② DBアクセス
        jdbcTemplate.update("INSERT INTO attendances ...");
        // ③ メール送信
        mailSender.send("上長へ通知...");
        // ④ CSV出力
        Files.write(Path.of("log.csv"), ...);
    }
}
```
**問題**：メールの文面を変えるときも、DBのカラムを増やすときも、業務ルールを変えるときも、**このクラスを触る**ことになります。触るたびに全部の動作確認が必要になり、事故のリスクが上がります。

```java
// ⭕ 良い：責務ごとに分割
@Service
public class AttendanceService {
    private final AttendanceValidator validator;
    private final AttendanceRepository repository;
    private final NotificationService notificationService;

    public AttendanceService(AttendanceValidator v, AttendanceRepository r, NotificationService n) {
        this.validator = v; this.repository = r; this.notificationService = n;
    }

    @Transactional
    public void register(AttendanceRegisterCommand command) {
        validator.validate(command);
        AttendanceEntity saved = repository.save(command.toEntity());
        notificationService.notifyOvertime(saved);
    }
}
```

**判定法**：「このクラスを説明するとき『〜と〜をする』と "と" が必要なら、責務が多すぎます。**"と" を使わずに1文で説明できるか**」がチェックポイントです。

#### O：開放閉鎖の原則（OCP）
**「拡張には開き、修正には閉じる」** — Day 4 でやった通りです。
新しい雇用形態が増えたとき、**既存のクラスを1行も変えずに、新しいクラスを追加するだけ**で対応できる形。

#### L：リスコフの置換原則（LSP）
**「子クラスは、親クラスと差し替えても正しく動くべき」**
```java
// 親：「保存できる」という約束
public class EmployeeStore {
    public void save(Employee e) { /* 保存する */ }
}

// ❌ 違反例：子が親の約束を破っている
public class ReadOnlyEmployeeStore extends EmployeeStore {
    @Override
    public void save(Employee e) {
        throw new UnsupportedOperationException("保存できません");
    }
}
```
親を期待して書かれたコードが、子を渡された途端に壊れます。**「継承したのに親の約束を守れない」なら、そもそも継承すべきではありません。**

#### I：インタフェース分離の原則（ISP）
**「使わないメソッドを実装させられる状況を作らない」**
```java
// ❌ 巨大インタフェース
public interface EmployeeManager {
    void hire(); void fire(); void promote();
    void calculateSalary(); void sendPayslip(); void exportCsv();
}
// ⭕ 用途ごとに分割
public interface EmployeeHiring { void hire(); void fire(); }
public interface SalaryCalculation { BigDecimal calculateSalary(String employeeId); }
```

#### D：依存性逆転の原則（DIP）
**「具体ではなく抽象に依存せよ」**
```java
// ❌ Service が具体クラスに依存
public class AttendanceService {
    private final PostgresAttendanceRepository repository;   // DB製品名が Service に漏れている
}
// ⭕ インタフェースに依存
public class AttendanceService {
    private final AttendanceRepository repository;           // 中身が何かは知らない
}
```
**Day 9 の DI は、この原則を実現するための仕組みです。** SOLID と Spring がここで繋がります。

### その他の原則
- **DRY**（同じことを2箇所に書くな）— ただし「たまたま今同じ」だけのコードを無理にまとめると、後で片方だけ変わるときに苦しみます。**「同じ理由で変わるもの」だけまとめる**のが正解
- **YAGNI**（将来使うかもで作るな）— 「拡張性のため」に作った仕組みの8割は使われず、読む人の負担になるだけです
- **KISS**（単純に保て）— 賢いコードより、退屈で読みやすいコードが勝ちます

### 命名：コードの読みやすさの8割

| 悪い | 良い | 理由 |
|---|---|---|
| `List<Employee> list` | `List<Employee> activeEmployees` | 何のリストか分かる |
| `int d` | `int workDays` | 略語は読めない |
| `getData()` | `findOvertimeRecordsByMonth()` | 何を返すか分かる |
| `flag` | `isRetired` | boolean は `is`/`has`/`can` で始める |
| `process()` | `calculateMonthlySalary()` | 「処理する」は情報量ゼロ |
| `tmp`, `data2`, `hoge` | — | 論外 |

**命名のコツ**
- **メソッド名は「動詞＋目的語」**：`calculateOvertimePay`, `findByEmployeeId`
- **`get` は単純な取得のみ**。計算や検索なら `calculate` / `find` / `search` を使う
- **長い名前を恐れない**。`calculateMonthlyOvertimePayForRegularEmployee` は良い名前です。短くて意味不明な名前より100倍まし
- **業務用語をそのまま使う**。仕様書が「打刻」なら `stamp` ではなく `clockIn`/`clockOut` など、チームで統一された語を使う

### リファクタリングの基本技

**① 長いメソッドを分割（メソッド抽出）**
```java
// Before: 80行のメソッド
public MonthlySummary calculate(String employeeId, int year, int month) {
    // データ取得 20行
    // 勤務時間集計 20行
    // 残業代計算 20行
    // 結果組み立て 20行
}
// After
public MonthlySummary calculate(String employeeId, int year, int month) {
    List<AttendanceEntity> records = fetchRecords(employeeId, year, month);
    WorkTime workTime = aggregateWorkTime(records);
    BigDecimal overtimePay = calculateOvertimePay(workTime, employeeId);
    return buildSummary(employeeId, year, month, workTime, overtimePay);
}
```
**目安：1メソッド20行以内、1画面に収まること。** 20行を超えたら分割を検討してください。

**② マジックナンバーを定数に**
```java
// ❌ if (workHours > 8)
// ⭕
private static final int STANDARD_WORK_HOURS = 8;
if (workHours > STANDARD_WORK_HOURS)
```

**③ ネストを浅くする（早期リターン）**
```java
// ❌ ネストが深い
public String judge(Employee e) {
    if (e != null) {
        if (e.isActive()) {
            if (e.getWorkHours() > 8) {
                return "残業";
            } else { return "定時"; }
        } else { return "休職中"; }
    } else { return "不明"; }
}
// ⭕ 早期リターン
public String judge(Employee e) {
    if (e == null) return "不明";
    if (!e.isActive()) return "休職中";
    if (e.getWorkHours() > 8) return "残業";
    return "定時";
}
```
**ネストは2段まで**を目安に。3段以上は読めなくなります。

**④ コメントの書き方**
```java
// ❌ 何をしているか（コードを読めば分かる）
i++;  // i を1増やす

// ⭕ なぜそうしているか（コードからは絶対に分からない）
// 法定労働時間は1日8時間（労働基準法32条）。就業規則第12条により当社も同様。
private static final int STANDARD_WORK_HOURS = 8;

// ⭕ 意図的な例外
// FIXME: 旧システム移行データに退勤時刻NULLが存在するため暫定でスキップ。2026/12までに移行完了予定（ATT-45）
if (entity.getClockOut() == null) continue;
```
**良いコメントは「なぜ」を書きます。「何を」はコードで表現してください。**

### コードレビュー

**レビューを受ける側の作法（新人はまずこちら）**
1. **セルフレビューを先にする**。自分のPRの差分を上から下まで読む。これで指摘の3割は自分で消せます

**レビューする側の作法（いずれ必要になります）**
- **人ではなくコードを指摘する**。「なぜこう書いたの？」ではなく「ここは〇〇にすると△△の利点があります」

### 【実務標準】Testcontainers — 本物のDBでテストする

**`@DataJpaTest` は、既定で「組み込みDB（H2）に差し替えて」テストを実行します。**
つまり何もしないと、**本番は PostgreSQL なのにテストだけ H2** という状態になります。方言の差でテストが素通りし、**本番でだけ落ちる**という最悪のパターンです。

**かといって、開発用DBをテストに使うのも間違いです。**
- テストは大量のデータを作っては消すので、**自分の動作確認データが毎回消えます**
- **テストの実行順や前回の残骸で結果が変わります**（FIRST原則の Independent 違反）
- CI サーバーには、そもそも「あなたのローカルDB」がありません

**現在の答えが Testcontainers です。** テスト開始時に **Docker で本物の PostgreSQL を使い捨てで起動し、終わったら破棄**します。

**依存を追加**（`attendance-api/pom.xml`）
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers-postgresql</artifactId>   <!-- ⚠ 接頭辞 testcontainers- が必要 -->
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers-junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
```
> **⚠ `org.testcontainers:postgresql` という古い書き方は使えません。** Testcontainers 2.0 で全モジュールが `testcontainers-` 接頭辞付きに改名されました。
> 古い名前のまま書くと `'dependencies.dependency.version' ... is missing` でビルドできません（Boot の BOM が新しい名前しか管理していないため）。
> **ネット上の記事はまだ旧名のものが大半です。** ライブラリのメジャーバージョンが上がったときは、**公式のリリースノートで名前の変更を確認する**——これも実務の作法です。

（バージョンは `spring-boot-starter-parent` が管理するので書きません。**バージョン管理を親に任せるのが実務の作法**で、ライブラリ同士の相性問題を避けられます）

**必要な import**
```java
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.postgresql.PostgreSQLContainer;      // ⚠ Testcontainers 2.x の新しい場所
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
```

**動きの理解（ここが大事）**
1. テストクラスの読み込み時に `PostgreSQLContainer` が Docker で `postgres:16` を起動する
2. `@ServiceConnection` が、**その都度変わる接続URL・ポート・パスワードを Spring に自動で渡す**（この仕組みが無かった頃は `@DynamicPropertySource` で手書きしていました）
3. **Flyway が自動で走り、`V1__*.sql` からテーブルが作られる**（＝本番と同じ手順でスキーマが再現される）
4. テストが終わるとコンテナは破棄される

> **`static` にしている理由**：`static` ならテストクラス内で**1回だけ起動**して全テストで共有します。メソッドごとに起動すると数十秒×件数かかり、「遅いテストは実行されなくなる」に直行します。
> **テスト間のデータ独立**は、コンテナを毎回作り直すのではなく **`@Transactional` による自動ロールバック**で担保するのが定石です。

> **【重要】これで「テストが1つのコマンドで、誰のPCでもCIでも同じように動く」状態になりました。**
> これは単なる便利機能ではありません。**「動作確認は手元でやりました」と言うしかない新人**と、**「CIで全部緑です」と言える新人**の差になります。
>
> **Docker が使えない環境の場合**：`docker compose` で起動したDBに対し、`@AutoConfigureTestDatabase(replace = NONE)` ＋ 専用のテスト用DB（`attendance_test`）で代替できます。ただし **CI では結局DBの用意が必要**になるため、可能な限り Testcontainers を選んでください。

```java
// ④ 結合テスト（全層を通す）
@SpringBootTest                    // ⚠ webEnvironment は既定（MOCK）のまま。理由は下の注記
@AutoConfigureMockMvc
@Testcontainers
@Transactional                     // テスト後に自動ロールバックされる
class AttendanceIntegrationTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

    @Autowired MockMvc mockMvc;

    @Test
    void 打刻登録から月次集計まで通しで動作する() throws Exception {
        // 打刻を登録
        mockMvc.perform(post("/api/attendances")...).andExpect(status().isCreated());
        // 集計を取得して検証
        mockMvc.perform(get("/api/employees/E001/summary?year=2026&month=8"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.totalWorkMinutes").value(480));   // フィールド名は仕様書 §3.3 に合わせる
    }
}
```

> **【落とし穴】`@Transactional` によるテスト後の自動ロールバックは、`webEnvironment = RANDOM_PORT` では効きません。**
> 実サーバを立てると、**テスト側のスレッドとサーバ側のスレッドが別**になり、テストが持っているトランザクションの外でDB操作が行われるためです（Spring Boot 公式リファレンスにも明記されています）。
>
> | 書き方 | HTTPの呼び方 | `@Transactional` のロールバック |
> |---|---|---|
> | `@SpringBootTest` ＋ `@AutoConfigureMockMvc` | `MockMvc`（サーバを立てない） | **効く** ← 本教材はこちら |
> | `@SpringBootTest(webEnvironment = RANDOM_PORT)` ＋ `TestRestTemplate` | 実サーバに本物のHTTP | **効かない**（後片付けは `@Sql` 等で自分でやる） |
>
> **「なんとなく強そうだから RANDOM_PORT」と書くと、データが残留してテストが不安定になります。** MockMvc で足りるなら MockMvc を使う、が原則です。

### 良いテストの条件（FIRST原則）
- **Fast**（速い）— 遅いテストは実行されなくなる
- **Independent**（独立）— テストの実行順序に依存しない。**他のテストの結果に依存するテストは最悪**
- **Repeatable**（再現可能）— 何度実行しても同じ結果。**`LocalDate.now()` を直接使うとある日突然壊れます**（時刻は外から注入する）
- **Self-validating**（自己検証）— 成功／失敗が自動で判定される。目視確認は不可
- **Timely**（適時）— 実装と同時か、その前に書く

### テストしにくいコードは、設計が悪いコード
**「テストが書きにくい」と感じたら、それはテストの問題ではなく設計の問題です。**
- `new` でハードコードしている → DIにする
- `static` メソッドに依存している → インタフェース経由にする
- `LocalDate.now()` を直接呼んでいる → `Clock` を注入する
- メソッドが100行ある → 分割する

**この気づきが、テストが「設計を改善する道具」でもある理由です。**

### CI（GitHub Actions）
`.github/workflows/ci.yml`
```yaml
name: CI
on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest        # このランナーには Docker が入っている＝Testcontainers がそのまま動く
    defaults:
      run:
        working-directory: attendance-api   # ⚠ pom.xml があるフォルダを指定する
    steps:
      - uses: actions/checkout@v5
      - name: Set up JDK 21
        uses: actions/setup-java@v5
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven
      - name: Build and test
        run: mvn -B clean verify
```

**このCIが実際にやっていること**
1. リポジトリを取得し、JDK 21 を用意する
2. `mvn clean verify` を実行 → **Testcontainers が PostgreSQL を起動し、Flyway がテーブルを作り、全テストが走る**
3. 1つでも落ちれば PR に赤いバツが付く

> **`.github/workflows/ci.yml` はリポジトリの一番上（`java-14days/.github/workflows/`）に置きます。** `pom.xml` はその下の `attendance-api/` にあるので、`working-directory` の指定を忘れると `no POM in this directory` で落ちます。**CI が最初に落ちる原因の定番です。**
>
> **DBの用意を CI 側に書いていないことに注目してください。** Testcontainers を使っていれば、**テストコード自身が必要なDBを起動する**ので、CI の設定は「JDKを入れてビルドするだけ」で済みます。
> **「CIの設定ファイルに環境構築の知識が溜まらない」ことが重要**です。CIにしか書かれていない設定は、手元で再現できず、壊れたときに誰も直せなくなります。
これで **PRを出すたび自動でビルドとテストが走ります**。テストが落ちているPRはマージできない設定にするのが実務の標準です。

### セキュリティ：新人が絶対に守る7項目

1. **SQLは文字列連結しない**（プレースホルダ／JPAを使う）→ SQLインジェクション対策
2. **パスワードは平文で保存しない**。`BCrypt` でハッシュ化する
3. **秘密情報をコードやGitに置かない**。環境変数／シークレット管理を使う
4. **エラーの詳細を利用者に返さない**（Day 11）
5. **ログに個人情報・パスワード・カード番号を出さない**
6. **入力は必ず検証する**。「クライアント側でチェックしているから大丈夫」は通用しない（**クライアントは改竄できる**）
7. **ライブラリを古いまま放置しない**。既知の脆弱性が入ります（OWASP Dependency-Check（`mvn org.owasp:dependency-check-maven:check`）や GitHub の Dependabot を使う）

**依存を追加します**（`attendance-api/pom.xml`）。
```xml
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-crypto</artifactId>
</dependency>
```

> **⚠ `spring-boot-starter-security` を入れてはいけません。**
> 検索すると真っ先に出てきますが、これを入れると **Spring Security の自動設定が全エンドポイントに認証をかけます**。
> その瞬間に **Day 9〜11 で作った curl の確認が全部 401 になり、`@WebMvcTest` / `@SpringBootTest` のテストも全部 401 で落ちます**。CI構築日に原因不明の全面赤を招く、典型的な事故です。
> **今日必要なのは「ハッシュ化の道具」だけ**なので、`spring-security-crypto` だけを入れます。認証・認可の仕組みそのものは 15日目以降の学習項目です。

```java
// パスワードの正しい扱い
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
// 保存時
String hash = passwordEncoder.encode(rawPassword);
// 照合時（復号はできない。ハッシュ同士を比較する）
boolean ok = passwordEncoder.matches(inputPassword, storedHash);
```

### 質問の技術（新人の評価を最も左右する要素）

**❌ 悪い質問**
> 「動きません。どうすればいいですか？」

**⭕ 良い質問（このテンプレートを使ってください）**
```
【やろうとしていること】
月次集計APIで、社員IDを指定して8月分の勤怠を取得したい

【起きていること】
GET /api/employees/E001/summary?year=2026&month=8 を叩くと 500 が返る

【エラー内容】
NullPointerException: Cannot invoke "AttendanceEntity.getClockOut()" because "entity" is null
  at AttendanceService.calculateWorkTime(AttendanceService.java:45)

【自分で調べたこと・試したこと】
・DBを直接見たところ、8月のデータは10件ありました
・デバッガで確認したところ、リストの3件目で clockOut が null でした
・退勤打刻が無い（打刻漏れ）レコードが原因だと推測しています

【聞きたいこと】
退勤打刻が無いレコードは、集計時にどう扱うのが業務的に正しいでしょうか？
（スキップ／エラー／当日の定時で補完 のどれか、あるいは他の方針か）

【期限感】
本日17時までに方針が決まれば、今日中に実装できます
```

**このテンプレートの何が良いか**
- 相手が **状況を再現するために聞き返す必要がない**
- **自分で調べたことが伝わる**（丸投げしていない）
- **技術の質問ではなく業務判断の質問だと明確**（先輩は即答できる）
- **期限感**があるので優先度を判断できる

> **「30分ルール」**：30分自力で調べて解決しなければ聞く。ただし**必ず上のテンプレートを埋めてから**聞く。テンプレートを埋めている間に自己解決することも多いです。

### 報告・連絡・相談
- **悪い報告ほど早く**。「間に合いません」は締切当日ではなく、**気づいた瞬間**に言う。早ければリカバリーできます
- **進捗は「％」ではなく「何が終わって何が残っているか」**で伝える。「80%です」は情報量がありません
- **仕様が曖昧なら実装前に確認する**。実装後の手戻りが最もコストが高い
- **勝手に仕様を決めない**。良かれと思った独自判断が最大のリスクです

### 見積りの考え方
- 見積りは「作業時間」だけでなく、**調査・テスト・レビュー対応・修正**を含める
- **経験則：実装時間の2〜3倍**が実際にかかる総時間
- 分からないものは「分かりません」と言い、**まず調査に半日ください**と言う（これは正しい対応です）
- 見積りを超えそうになったら、**超える前に**報告する

### チケットの扱い
- 着手時にステータスを「進行中」にする（誰が何をしているか可視化）
- 完了条件（受け入れ条件）を着手前に確認する
- **チケットに書かれていないことは、勝手にやらない**（スコープ外の変更は別チケットに）
