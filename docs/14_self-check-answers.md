# 第1週（Day 0〜7）

## Day 0：地図を手に入れる

**1. JDK と JVM の違いを説明できる**
JDKは開発に必要な道具一式（コンパイラ・実行環境等）。JVMはコンパイル済みの`.class`ファイルを実際に動かすエンジン。JDKの中にJVMが含まれるという包含関係。

**2. コンパイルとは何をする作業か説明できる**
人間が書いた`.java`のソースコードを、JVMが読める中間形式である`.class`ファイル（バイトコード）に翻訳する作業。文法が間違っているとこの段階でエラーになる。

**3. `.java` と `.class` の違いを説明できる**
`.java`は人間が書くソースコード（テキスト）。`.class`はそれをコンパイルした後にできる、JVMが実行できるバイトコード（中間形式）。

**4. ターミナルから `java -version` と `git --version` が実行できる**
（実施確認）両方のコマンドがエラーなくバージョン番号を表示すればOK。

**5. GitHub に自分のコードが上がっている（ブラウザで見える）**
（実施確認）ブラウザでリポジトリを開き、pushしたファイルが表示されればOK。

**6. エラーメッセージを3種類見て、それぞれ何を意味するか自分の言葉で説明できる**
セミコロン抜け＝構文エラー（文の終わりが認識できない）、メソッド名のタイプミス＝シンボルが見つからない（存在しないメソッドを呼んでいる）、文字列の閉じ忘れ＝文字列リテラルが閉じられていない。3種の典型的なコンパイルエラーを区別できること。

**7. `week1` で `mvn clean test` が BUILD SUCCESS になる**
（実施確認）Mavenプロジェクトとして正しくビルドできる状態になっていること。

**8. `docker run --rm hello-world` が動く**
（実施確認）Dockerが正常にインストールされ、コンテナを実行できる状態になっていること。

## Day 1：変数・型・メソッド

**1. `int` と `double` と `String` と `boolean` の違いを説明できる**
`int`=整数、`double`=小数、`String`=文字列（参照型）、`boolean`=真偽値。前3つとcharなどを合わせてプリミティブ型と呼び、`String`だけは参照型。

**2. 金額計算に `double` を使ってはいけない理由を説明できる**
コンピュータは2進数で小数を表現するため、`0.1+0.2`が`0.30000000000000004`になるなど誤差が出る。金額計算で1円でもズレると業務事故になるため、正確な10進計算ができる`BigDecimal`を使う。

**3. `7 / 2` が 3 になる理由を説明できる**
両辺が`int`型（整数）同士の割り算なので、結果もintとして扱われ小数部分が切り捨てられる。小数の結果が欲しければ、どちらかを`(double)`にキャストする。

**4. NullPointerException が起きる原因を説明できる**
何も指していない（null）変数に対して、メソッド呼び出しやフィールドアクセスなど「矢印の先を見に行く」操作をしようとしたときに発生する実行時エラー。

**5. メソッドの「引数」と「戻り値」を説明できる**
引数はメソッドに渡す入力値、戻り値はメソッドが処理結果として呼び出し元に返す値。`void`の場合は戻り値がない。

**6. `void` の意味を説明できる**
そのメソッドが値を返さないことを示す型。`main`メソッドはJVMから直接呼ばれ戻り値を使う先が無いため`void`になっている。

**7. クラス名・メソッド名・変数名の命名ルールを説明できる**
クラス名は大文字始まりの名詞（PascalCase）、メソッド名・変数名は小文字始まりの動詞/名詞（camelCase）、定数は全部大文字+アンダースコア。名前だけで役割が分かることが目的。

**8. 計算処理と表示処理を分けるべき理由を説明できる**
出力先が画面からCSVやAPIレスポンスに変わっても計算ロジックを再利用できるようにするため。1つのメソッドが複数の役割を持つと、変更時の影響範囲が広がりテストもしづらくなる。

## Day 2：制御構文・配列・文字列・エラーの読み方

**1. `==` と `equals` の違いを説明できる**
`==`はプリミティブ型なら値そのもの、参照型なら「同じメモリ上の場所（インスタンス）を指しているか」を比較する。`equals`は中身（内容）が同じかどうかを比較するメソッド。

**2. 文字列比較に `==` を使ってはいけない理由を説明できる**
同じ内容の文字列でも、`new`で作った別々の`String`インスタンスは異なるオブジェクトなので`==`はfalseになりうる。内容を比較したいときは必ず`equals`を使う。

**3. 配列のインデックスが0から始まることと、その落とし穴を説明できる**
配列の要素は0番目から数えるため、要素数がNならインデックスは`0〜N-1`。うっかり`<=`を使うなどして末尾を超えると`ArrayIndexOutOfBoundsException`になる。

**4. 拡張for文と通常のfor文の使い分けを説明できる**
インデックス番号自体が不要な「全要素をただ処理したいだけ」の場合は拡張for文（可読性が高い）。インデックス操作（特定位置だけ処理、逆順、複数配列を同時に回す等）が必要なら通常のfor文。

**5. スタックトレースを見て、自分のコードのどの行が原因か特定できる**
`at`行のうち、一番上にある「自分が書いたファイル名」が出ている行を探す。それより下はライブラリ内部の呼び出し経路なので無視してよい。

**6. ブレークポイントを置いてデバッガで変数の中身を確認できる**
（実施確認）行番号の左をクリックしてブレークポイントを設定し、デバッグ実行で停止させ、Variablesパネルで値を確認できること。

**7. F8（ステップオーバー）と F7（ステップイン）の違いを説明できる**
F8は現在行を実行して次の行へ進む（メソッド呼び出しの中には入らない）。F7はメソッド呼び出しがあればその中に踏み込んで1行ずつ追える。

**8. 空配列など「異常な入力」への備えが必要な理由を説明できる**
本番環境では「あり得ない」と思ったデータが実際に来る（新人社員でまだ勤怠が無い等）。正常系だけ動くコードは未完成で、異常な入力でも落ちずに処理できることがプロの仕事。

## Day 3：クラスとオブジェクト

**1. クラスとインスタンスの違いを説明できる**
クラスは設計図（型の定義）、インスタンスはその設計図から作られた実体。1つのクラスから複数のインスタンスを作れる（たい焼きの型とたい焼き）。

**2. なぜ配列を並べるよりクラスにまとめる方が良いのか説明できる**
複数の配列を並行管理すると、要素の削除・並べ替えでインデックスがズレて対応関係が壊れる事故が起きる。関連するデータと処理を1つのクラスにまとめることでこれを防げる。

**3. コンストラクタは何をするものか説明できる**
オブジェクトが生成される瞬間に1回だけ呼ばれる初期化専用のメソッド。フィールドへの値のセットや、不正な値を弾く引数チェックを行う。

**4. `this` が何を指すか説明できる**
「今まさに作られている・呼ばれているこのオブジェクト自身」を指す参照。フィールドと引数が同名のときに区別するために使う。

**5. カプセル化の目的を「隠すため」以外の言葉で説明できる**
フィールドをprivateにし変更を必ずメソッド経由にすることで、オブジェクトが常に正しい状態を保てるようにする仕組み。「隠す」ことでなく「不正な状態を作らせない」ことが目的。

**6. セッターを全フィールドに機械的に作ってはいけない理由を説明できる**
全フィールドにセッターを作るとpublicフィールドと同じ状態になり、カプセル化の意味が消える。業務上本当に変更されうる項目だけに、業務イベントを表す名前（`changeDepartment`等）でメソッドを作るべき。

**7. static変数とインスタンス変数の違いを説明できる**
static変数はクラス全体で1つだけ共有される変数。インスタンス変数はオブジェクトごとに個別に持つ変数。

**8. 実務で static を多用すべきでない理由を説明できる**
static変数は全体で共有されるため、複数の処理が同時に動く環境では値が予期せず書き換わる（スレッドセーフでない）事故につながる。定数や純粋な計算ユーティリティ以外での使用は避ける。

**9. コンストラクタで引数チェックをする理由を説明できる**
不正な値（null、空文字、範囲外の数値等）を持ったオブジェクトが生成されると、後からその不整合の原因を追跡するのが困難になる。生成時点で弾くことで「常に正しい状態」を保証できる。

**10. `toString()` をオーバーライドする理由を説明できる**
デフォルトの`toString()`はクラス名とハッシュ値しか表示せずデバッグの役に立たない。オーバーライドしてフィールドの中身が見えるようにすることで、ログ出力やデバッグ時に状態を把握しやすくなる。

## Day 4：継承・インタフェース・多態性

**1. インタフェースとは何か、1文で説明できる**
「こういうメソッドを持つこと」という約束（契約）だけを定義したもので、中身の実装は持たない。

**2. ポリモーフィズムが「何の問題を解決するのか」を説明できる**
呼び出す側が「相手が具体的に何のクラスか」を知らなくても、同じ呼び方で異なる振る舞いをさせられる。新しい種類が増えても呼び出し側のコードを変更せずに済む。

**3. if 分岐で書いた場合と比べて、インタフェースの利点を説明できる**
if分岐で雇用形態ごとの処理を書くと、種類が増えるたびに既存メソッドを修正する必要があり、修正のたびに動作確認が必要になる。インタフェースなら新しい実装クラスを追加するだけで済む。

**4. 継承よりインタフェースを優先すべき理由を説明できる**
継承は親の実装ごと引き継ぐため、親を変更すると全ての子に影響する密結合になる。またJavaは多重継承ができない。インタフェースはより緩い結合で、複数実装も可能。

**5. 継承を使ってよい条件（is-a関係）を説明できる**
「子は親の一種である」（is-a）が100%成立するときだけ使う。例：`Manager is a Employee`は成立するが、`AttendanceService is a DatabaseConnection`は成立しない（この場合は持つ＝委譲にする）。

**6. 抽象クラスとインタフェースの使い分けを説明できる**
共通の処理の流れを親に実装として持たせつつ、一部だけ子に書かせたいときは抽象クラス（テンプレートメソッドパターン）。実装を一切持たず「約束」だけを定義し、複数の型をまたいで実装させたいときはインタフェース。

**7. String ではなく enum を使うべき理由を説明できる**
Stringで種別を表すとスペルミス（`"REGULER"`等）があってもコンパイルは通り、実行時に初めてバグとして表面化する。enumなら存在しない値の指定はコンパイルエラーになる。

**8. record が何を自動生成してくれるか説明できる**
コンストラクタ、各フィールドのゲッター、`equals`、`hashCode`、`toString`を自動生成してくれる。データを持つだけの不変（イミュータブル）なクラスを1行で書ける。

**9. `@Override` を書く意味を説明できる**
親のメソッドを上書きしているつもりで実は違うシグネチャを書いてしまった、というミスをコンパイル時に検出できる。付け忘れると、上書きしたつもりが別の新しいメソッドとして扱われていることに気づけない。

## Day 5：コレクション・Optional・Stream

**1. List / Map / Set の使い分けを説明できる**
Listは順序があり重複を許す入れ物、Mapはキーと値のペアで管理する入れ物、Setは重複を許さない入れ物。データの性質に応じて選ぶ。

**2. `List<String> x = new ArrayList<>();` の左辺をインタフェース型にする理由を説明できる**
インタフェース型で受けることで、後から`LinkedList`等の別実装に差し替えても使う側のコードを一切変更せずに済む（多態性の実践）。現場ではこの書き方が標準。

**3. equals をオーバーライドしたら hashCode も必要な理由を説明できる**
`HashMap`や`HashSet`はまず`hashCode`で格納先の「引き出し」を決め、その中で`equals`で中身を比較する。`hashCode`が違うと別の引き出しに入り、`equals`が呼ばれず「同じはずなのに別物」と判定される。

**4. Optional を使う目的と、使うべき場所（戻り値）を説明できる**
「値があるかもしれないし無いかもしれない」ことを型で表現し、呼び出し側にNullPointerExceptionへの対処を強制させるため。使うのはメソッドの戻り値のみで、フィールドや引数には基本使わない。

**5. ラムダ式の読み方を説明できる**
`(引数) -> 処理` の形で読む。「その場限りの短い処理を渡す」ための書き方で、匿名クラスの簡略版にあたる。

**6. filter / map / collect のそれぞれの役割を説明できる**
`filter`は条件に合う要素だけ絞り込む、`map`は各要素を別の形に変換する、`collect`は最終的にリストやマップなど具体的な形にまとめて取り出す（終端操作）。

**7. groupingBy を使って集計が書ける**
（実施確認）`Collectors.groupingBy`で、特定のキーごとにグループ化した集計（合計・件数等）を書けること。

**8. Stream を使いすぎない方がよい場合があることを説明できる**
3〜4段を超えてネストしたStreamは、短く書けても読みにくくなる。「短く書く」ことより「読んで分かる」ことが優先されるべきで、複雑な場合はfor文の方が適切なこともある。

## Day 6：例外設計・日時・BigDecimal・ログ・ビルドツール

**1. 検査例外と非検査例外の違いを説明できる**
検査例外（Checked）はtry-catchかthrowsが強制される、呼び出し側が回復できる可能性のある異常（`IOException`等）。非検査例外（Unchecked/RuntimeException）は強制されず、プログラムのバグや引数不正を表す（`NullPointerException`等）。

**2. 例外を握りつぶしてはいけない理由を説明できる**
catchして何もしないと、障害が実際に起きていても誰も気づけなくなり原因調査が不可能になる。ログに出す・投げ直す・明確に回復する、のいずれかを必ず行う。

**3. `log.error("失敗")` と `log.error("失敗", e)` の違いを説明できる**
例外オブジェクト`e`を渡さないと、スタックトレース（原因の手がかり）がログから消える。`e`を渡せば発生箇所や原因の連鎖まで記録される。

**4. try-with-resources が必要な理由を説明できる**
ファイルやDB接続などのリソースは、例外が起きても確実に閉じないと資源が枯渇してシステムが停止する。try-with-resourcesを使うと例外の有無にかかわらず自動でcloseされる。

**5. `java.util.Date` を使わない理由を説明できる**
`Date`と`Calendar`は可変（ミュータブル）でスレッドセーフでなく扱いにくい仕様のため、バグの温床として知られている。Java 8以降はより安全な`java.time`パッケージ（`LocalDate`等）が標準。

**6. `LocalDate` / `LocalTime` / `LocalDateTime` / `Duration` を使い分けられる**
`LocalDate`は日付のみ、`LocalTime`は時刻のみ、`LocalDateTime`は日付+時刻を扱う。`Duration`は2つの時刻・日時の間の「期間」を表す。

**7. `new BigDecimal("0.1")` と `new BigDecimal(0.1)` の違いを説明できる**
doubleの`0.1`はコンピュータの2進数表現の時点で既に誤差を含んでいるため、数値でBigDecimalを作るとその誤差がそのまま入る。文字列で渡せば書いた通り正確な値になる。

**8. BigDecimal の割り算で丸めモードが必須な理由を説明できる**
割り切れない小数は無限に続く可能性があり、`BigDecimal`はどこで打ち切るか（何桁で、どう丸めるか）を明示的に指定しないと例外を投げる仕様になっている。

**9. ログレベル4種の使い分けを説明できる**
`debug`は開発時の詳細情報、`info`は通常の記録（正常な処理の節目）、`warn`は注意（異常の兆候）、`error`は実際に発生した異常。本番では`info`以上を出すのが一般的。

**10. ログに `+` で文字列連結しない理由を説明できる**
プレースホルダ（`{}`）でなく文字列連結を使うと、そのログレベルが出力されない設定であっても連結処理自体は毎回実行されてしまい、無駄な性能コストがかかる。

**11. `pom.xml` にライブラリを追加できる**
（実施確認）`<dependencies>`の中に`groupId`・`artifactId`・`version`を指定した`<dependency>`を追加し、Mavenパネルで再読み込みできること。

## Day 7：Git実務フロー と 単体テスト

**1. ブランチを切ってPRを出すまでの流れを説明できる**
`main`をpull → ブランチを切る → コードを書く → status/diffで確認 → add → commit → push → GitHubでPRを作成、という流れ。

**2. `main` を保護し、直接 push を禁止する理由を説明できる**
`main`は常にリリース可能な状態を保つ必要がある。誰かが壊れたコードを直接pushすると、それ以降の全員の作業が壊れたコードの上に積み上がる。PRとCI通過を仕組みとして強制することで防ぐ。

**3. `git add .` を避けるべき理由を説明できる**
意図しないファイル（一時ファイル、ログ、秘密情報など）まで一緒にステージングされる事故が多い。ファイル名を指定して、載せるものを毎回意識するほうが安全。

**4. コミットメッセージの良い書き方を説明できる**
`feat:`/`fix:`/`docs:`等のプレフィックスを付け、「何を」「なぜ」変更したかが分かる具体的な文にする。「修正」「いろいろ」のような情報量のないメッセージは避ける。

**5. 1コミットの粒度をどう決めるか説明できる**
1コミット＝1つの意味のある変更、にする。機能追加・バグ修正・フォーマット整形を1つのコミットに混ぜない。問題が起きたときにそのコミットだけを取り消せるようにするため。

**6. `.gitignore` に何を入れるべきか説明できる**
ビルド生成物（`target/`、`*.class`）、IDE/エディタの個人設定（`.idea/`、`.obsidian/`）、OS固有ファイル、秘密情報を含む設定ファイル、ログファイルなど、「他人には無意味、または漏れると危険」なものを入れる。

**7. 認証情報をコミットしてはいけない理由を説明できる**
一度GitHubに上げると、後から削除しても履歴に永久に残ってしまう。パスワードやAPIキーが漏洩すると実際の重大インシデントに直結する。

**8. コンフリクトを自力で解決できる**
（実施確認）`<<<<<<<` / `=======` / `>>>>>>>` のマーカーを全て削除し、正しい最終形に整えてadd/commitできること。

**9. 単体テストを書く理由を3つ説明できる**
①手動確認は再現できないが自動テストは何度でも同じ確認を繰り返せる、②リファクタリング時に壊していないことを確認できる、③テストコード自体が仕様書として機能する。

# 第2週（Day 8〜14）

## Day 8：データベースとSQL

**1. 主キーと外部キーの役割を説明できる**
主キーはそのテーブルの各行を一意に特定するための列（重複・NULL不可）。外部キーは他テーブルの主キーを参照し、存在しないデータへの参照を防ぐ（参照整合性を保つ）。

**2. NOT NULL や UNIQUE を DB に設ける理由（アプリ側チェックだけでは不十分な理由）を説明できる**
アプリのコードにバグがあったり、複数の経路からDBに書き込まれたりすると、アプリ側のチェックだけでは不正なデータの混入を防ぎきれない。DB自体に制約を持たせることで最後の砦として弾ける。

**3. 正規化の目的を説明できる**
同じ情報を複数箇所に重複して持たないようにすること。重複を許すと、更新時にどちらか一方だけ変更されて矛盾（更新漏れ）が生じるリスクがある。

**4. `WHERE` と `HAVING` の違いを説明できる**
`WHERE`は集計（`GROUP BY`）を行う前の行の絞り込み。`HAVING`は集計した後の結果に対する絞り込み。

**5. INNER JOIN と LEFT JOIN の違いを説明できる**
`INNER JOIN`は両方のテーブルに存在するデータだけを結合する。`LEFT JOIN`は左側（FROM側）は全件残し、右側に対応が無ければNULLで埋める。

**6. トランザクションが必要な理由を具体例で説明できる**
例えば口座間の送金で「引き落としだけ成功して入金が失敗」のような中途半端な状態を防ぐため。`BEGIN`〜`COMMIT`の間の操作は全て成功するか、全て取り消される（ロールバック）かのどちらかになる。

**7. インデックスの利点と欠点を説明できる**
利点は検索が劇的に速くなること。欠点は書き込み（INSERT/UPDATE）のたびにインデックスも更新する必要があり、書き込みが遅くなること。付けすぎは逆効果。

**8. SQLインジェクションが何か、どう防ぐか説明できる**
ユーザー入力をそのままSQL文に文字列連結すると、悪意ある入力によって意図しないSQLが実行される脆弱性。プレースホルダ（`?`）を使った`PreparedStatement`やJPAを使い、入力値がSQLの構造に混ざらないようにして防ぐ。

**9. N+1問題を説明でき、対策を1つ以上言える**
一覧を1回のクエリで取得した後、各要素に対して関連データを取得するクエリを個別に発行してしまい、件数分（N回）＋最初の1回でクエリが大量発行される問題。`JOIN FETCH`でまとめて1回のクエリで取得することで解消できる。

**10. UPDATE/DELETE 実行前にやるべきことを説明できる**
同じWHERE条件でまず`SELECT`し、対象件数と内容が意図通りか確認してから実行する。WHERE忘れによる全件更新・削除の事故は実際に多発している。

**11. `docker compose up -d` / `down` / `down -v` の違いを説明できる**
`up`はコンテナを起動（`-d`はバックグラウンド実行）。`down`は停止してコンテナを削除するがデータ（volume）は残す。`down -v`はvolumeごと削除しデータも全て消える。

**12. 開発と本番で違うDB製品を使うと何が起きるか説明できる**
日時計算や文字列関数などSQLの「方言」が製品ごとに異なるため、開発環境（例：H2）では動いたSQLが本番（PostgreSQL）で動かない、という事故が起きる。開発から本番まで同じ製品を使うことでこれを防ぐ。

**13. イメージのバージョンを固定する理由（`postgres:18` と `postgres:latest`）を説明できる**
`latest`を指定すると、ある日突然メジャーバージョンが上がって動作が変わったり動かなくなったりする。`postgres:18`のようにバージョンを明示的に固定することで、本番と同じ環境を安定して再現できる。

## Day 9：Web・HTTP・REST・Spring Boot入門

**1. HTTPのリクエストとレスポンスの構造を説明できる**
リクエストはクライアントからサーバへの「メソッド＋URL＋ヘッダ＋（あれば）ボディ」。レスポンスはサーバからクライアントへの「ステータスコード＋ヘッダ＋（あれば）ボディ」という構造。

**2. GET / POST / PUT / DELETE の使い分けを説明できる**
GETは取得（何も変更しない）、POSTは新規作成、PUTは全体を置き換える更新、DELETEは削除。操作の種類をHTTPメソッドで表現する。

**3. 200 / 201 / 400 / 404 / 500 をそれぞれいつ返すか説明できる**
200は取得・更新成功、201は作成成功、400はリクエスト自体が不正（バリデーションエラー等）、404は指定リソースが存在しない、500はサーバ側の想定外のエラー。

**4. エラーを全部500で返してはいけない理由を説明できる**
クライアント起因のエラー（不正な入力等）まで500にすると、利用者は「自分が悪いのかサーバが落ちているのか」を判断できない。原因の所在に応じて適切なステータスを返す必要がある。

**5. REST的なURL設計（名詞を使う）を説明できる**
URLは操作対象の「モノ（リソース）」を名詞で表し、動詞（`getEmployee`等）を入れない。操作の種類はHTTPメソッドで表現する（例：`GET /api/employees/E001`）。

**6. DIとは何か、何のためにあるか説明できる**
クラスが必要とする依存オブジェクトを自分でnewするのではなく、外部（フレームワーク）から渡してもらう仕組み。テスト時に本物の代わりにモックを注入できる、実装の差し替えが容易になる、といった利点がある。

**7. DI無しだとテストが書けない理由を説明できる**
クラス内部で具体的な依存クラスをnewしていると、テスト時にも本物のDB接続などが強制的に動いてしまい、高速で安定したテストが書けない。DIで外から渡せるようにすることでモックに差し替えられる。

**8. Bean とは何か説明できる**
Springが管理する（インスタンス化・注入を行う）オブジェクトのこと。`@Service`, `@Repository`, `@RestController`等を付けたクラスがBeanとして自動的に登録される。

**9. コンストラクタインジェクションを推奨する理由を説明できる**
フィールドをfinalにでき不変にできる、テスト時に`new`で普通にモックを渡せる、必須の依存が無いとコンパイルが通らない、といった利点がある。フィールドインジェクション（`@Autowired`フィールド）はこれらができず現場では非推奨。

**10. IoC（制御の反転）が何の反転か説明できる**
通常は自分のコードが依存するオブジェクトを自分でnewして「制御」するが、DIではフレームワークがオブジェクトを作って渡してくれる（制御される側になる）。「誰が作るか」の主導権の逆転を指す。

## Day 10：レイヤードアーキテクチャとDB連携

**1. 3層それぞれの責務を説明できる**
Controller（受付）はHTTPの受け取りとServiceの呼び出しのみ、Service（頭脳）は業務ルールとトランザクション境界、Repository（倉庫番）はDBへの読み書きのみを担当する。

**2. 依存が一方向であるべき理由を説明できる**
Controller→Service→Repositoryの一方向にすることで、DB製品の変更などの影響をRepository層だけに閉じ込められ、上位層への影響を防げる。

**3. Controller に業務ロジックを書いてはいけない理由を説明できる**
Controllerに業務ロジックが漏れると、HTTP以外の経路（バッチ処理等）から同じ業務ロジックを再利用できなくなる。層の役割分担が崩れ、テストもしづらくなる。

**4. Entity と DTO を分ける理由を3つ説明できる**
①Entityをそのまま返すとパスワードハッシュ等の機密情報が漏洩する、②DBのカラム変更がそのままAPI仕様の変更になる、③JPAの遅延読み込みが絡んで意図しないSQLが発行されることがある。

**5. Entity をそのままAPIで返すセキュリティリスクを説明できる**
`passwordHash`や`hourlyRate`（給与情報）など、外部に見せるべきでない項目までレスポンスに含まれ、実際のセキュリティ事故につながる。

**6. `@Transactional` が何をするか説明できる**
メソッド開始時にトランザクションを開始し、正常終了時にCOMMIT、例外発生時に自動的にROLLBACKする。

**7. トランザクション境界を Service に置く理由を説明できる**
Serviceは複数のRepository呼び出しをまたぐ業務単位の処理を担当するため、その単位で「全部成功か全部取り消しか」を保証する必要がある。

**8. `@Transactional` が同一クラス内呼び出しで効かないことを知っている**
Springはプロキシという仕組みで`@Transactional`を実現しているため、外部から呼ばれた場合のみ介入できる。同じクラス内で`this.method()`のように呼ぶとプロキシを経由せず素通りする。

**9. `ddl-auto: update` を本番で使ってはいけない理由を説明できる**
`update`は差分を見て自動でALTERするため、列の削除や型変更を正しく反映できずデータ不整合の原因になる。本番では`validate`（検証のみ）にし、スキーマ変更はFlyway等のマイグレーションで管理する。

**10. パスワードを設定ファイルに直書きしない理由を説明できる**
設定ファイルはリポジトリにコミットされるため、直書きするとGitの履歴に永久に残る。環境変数やシークレット管理から読み込む必要がある。

**11. N+1問題を実際に起こして解消できる**
（実施確認）`@ManyToOne`のデフォルト（EAGER）や単純なループでN+1を発生させ、ログでクエリ本数を確認した上で、`JOIN FETCH`で1本にまとめられること。

## Day 11：バリデーション・例外ハンドリング・設定管理

**1. `@Valid` を付け忘れるとどうなるか説明できる**
`@NotBlank`等の制約アノテーションを付けていても、Controller引数に`@Valid`を付け忘れると検証が一切実行されず、不正な値がそのままServiceまで届く。

**2. `@Valid`（リクエストボディ）と、引数に付ける制約アノテーション（クエリ／パス変数）の使い分けを説明できる**
リクエストボディ（JSON）の検証は引数に`@Valid`を付ける。クエリパラメータやパス変数の検証はSpring Boot 4（Spring Framework 6.1）以降、制約アノテーションを引数に直接付けるだけで組み込みで検証される。

**3. Controller クラスに `@Validated` を付けてはいけない理由を説明できる**
クラスに付けると古いAOPプロキシ経由の検証が優先され、組み込みのメソッド検証が無効化される。飛ぶ例外も`HandlerMethodValidationException`から`ConstraintViolationException`に変わり、ハンドラで拾い漏れると意図せず500になる。

**4. 型変換の失敗や壊れたJSONが500にならないよう、400を明示的に返している**
（実施確認）`MethodArgumentTypeMismatchException`や`HttpMessageNotReadableException`を個別にハンドリングし、400を返すようになっていること。

**5. Controller と Service でチェックすべき内容の違いを説明できる**
Controllerでは形式チェック（必須項目、桁数、形式など単体で判断できるもの）、Serviceでは業務チェック（DBを見ないと分からない重複確認や業務ルール）を行う。

**6. 重複チェックが Controller でできない理由を説明できる**
重複しているかどうかはDBの中身を見ないと判定できないため、DBにアクセスするServiceの責務になる。

**7. `@RestControllerAdvice` の役割を説明できる**
全Controllerで発生した例外を1箇所にまとめてハンドリングし、統一されたエラーレスポンスを返す仕組み。

**8. エラーレスポンスを統一する理由を説明できる**
バラバラな形式のエラーだと、API利用者側でエラー処理のコードが複雑になる。統一形式にすることで、利用者は1つのパターンだけでエラーハンドリングできる。

**9. 500エラーで例外の詳細を返してはいけない理由を説明できる**
スタックトレースや例外メッセージをそのまま返すと、DBのテーブル名や内部構造が攻撃者に漏れる。詳細はログにのみ記録し、利用者には一般的なメッセージとtraceIdだけを返す。

**10. traceId が障害調査でなぜ役立つか説明できる**
1リクエストに一意なIDを振ってログ全行に付与することで、問い合わせを受けた際にそのIDだけでログから該当処理の全経路を一発で特定できる。

**11. MDC を clear する必要がある理由を説明できる**
サーバはスレッドを使い回すため、clearしないと前のリクエストのtraceIdが次のリクエストのログに紛れ込んでしまう。

**12. プロファイルの使い分けを説明できる**
local/dev/prod等の環境ごとに、DB接続先やログレベルなど異なる設定を切り替えるための仕組み。起動時に`--spring.profiles.active`で指定する。

**13. 秘密情報を環境変数から読む理由を説明できる**
設定ファイルに直書きするとGitにコミットされ漏洩リスクがある。環境変数から読むことで、コードやリポジトリと秘密情報を分離できる。

## Day 12：設計原則・命名・リファクタリング・コードレビュー

**1. SOLID の5つをそれぞれ具体例で説明できる**
S単一責任（1クラス1つの理由でしか変更されない）、O開放閉鎖（拡張には開き修正には閉じる）、Lリスコフの置換（子は親と差し替えても正しく動く）、Iインタフェース分離（使わないメソッドを実装させない）、D依存性逆転（具体ではなく抽象に依存する）。

**2. 単一責任かどうかの判定法（"と"テスト）を説明できる**
そのクラスの役割を1文で説明しようとしたとき「〜と〜をする」のように"と"が必要になるなら、責務が多すぎるというサイン。

**3. DIP と Spring の DI の関係を説明できる**
DIP（依存性逆転の原則）は「具体クラスではなくインタフェースに依存せよ」という設計原則。SpringのDIはその原則を実現するための具体的な仕組み（実装クラスを外部から注入する）にあたる。

**4. DRY を機械的に適用すべきでない場合を説明できる**
たまたま今のコードが似ているだけで、将来別々の理由で変わっていく可能性があるものを無理に共通化すると、後で片方だけ変更したいときに苦しくなる。「同じ理由で変わるもの」だけをまとめるのが正解。

**5. YAGNI の意味と、なぜ重要かを説明できる**
"You Aren't Gonna Need It"（今使わないものは作るな）。将来のための拡張性を先回りして作っても、その多くは実際には使われず、読む人の理解負担だけが増える。

**6. 良い変数名／メソッド名の条件を5つ挙げられる**
意味が読み取れる、略語を使わない、booleanは`is`/`has`/`can`で始める、動詞から始める（メソッド）、長さを恐れない（短くて意味不明より長くて明確な方が良い）等。

**7. 早期リターンでネストを減らせる**
（実施確認）異常系・特殊系をif文の先頭でreturnして処理から抜けさせ、正常系のネストを浅く保てること。

**8. 「なぜ」を書くコメントと「何を」を書くコメントの違いを説明できる**
「何を」はコードを読めば分かるので不要（`i++; // iを1増やす`など）。「なぜ」はコードだけでは分からない背景（法律上の理由、過去の不具合対応等）を説明するもので、これだけ書く価値がある。

**9. レビューを受ける側の作法を5つ挙げられる**
セルフレビューを先にする、PRを小さく保つ、説明文をきちんと書く、指摘は人格否定ではないと理解する、対応したら「対応しました」と返信する等。

**10. レビュー指摘に重要度を付ける意味を説明できる**
`[must]`（必須）`[want]`（要望）`[nits]`（好み）等で重要度を示すことで、レビューを受ける側が優先順位をつけて対応でき、些細な指摘に時間を取られすぎるのを防げる。

**11. リファクタリングと機能追加を混ぜてはいけない理由を説明できる**
2つを1つのPRに混ぜると、レビュアーが「動作を変えた部分」と「変えていない部分」を差分から区別できなくなり、レビューの質が落ちる。別コミット・別PRに分けるべき。

**12. 他人のプロジェクトのリクエスト1本を、Controller から DB まで追える（petclinicで実施した）**
（実施確認）Ctrl+Bで定義へジャンプしながら、1つのエンドポイントがController→Service→Repository→DBまでどう繋がっているかを図に描いて説明できること。

## Day 13：テスト戦略・CI・セキュリティ最低限

**1. テストピラミッドを説明できる**
単体テストを土台に最も厚く、結合テストを中間、E2Eテストを頂点（最も少なく）にする構成。上に行くほど遅く壊れやすいため、下を厚くするのが原則。

**2. 単体テストと結合テストの使い分けを説明できる**
単体テストは1つのクラス・メソッドをモックを使って高速に検証する。結合テストは複数の層をまたいで実際の連携が正しいかを（本物のDB等を使って）検証する。

**3. `@WebMvcTest` と `@SpringBootTest` の違いを説明できる**
`@WebMvcTest`はController層とHTTP周りだけをテストする軽量なスライス（Serviceはモック）。`@SpringBootTest`はアプリ全体のコンテキストを起動する、より重い結合テスト用のアノテーション。

**4. モックを使う理由を説明できる**
依存先（DB接続等）を本物にせず偽物に差し替えることで、テストが高速かつ安定して実行できるようになる。

**5. FIRST原則の5つを説明できる**
Fast（速い）、Independent（独立している）、Repeatable（再現可能）、Self-validating（自己検証できる）、Timely（適時に書く）。

**6. `LocalDate.now()` を直接使うとテストが壊れる理由を説明できる**
実行するタイミングによって値が変わるため、月末や年末をまたぐと突然テストが失敗することがある。Clockを注入して固定できるようにすることで、いつ実行しても同じ結果になる。

**7. 「テストしにくい＝設計が悪い」を具体例で説明できる**
newでハードコードした依存、staticメソッドへの依存、`LocalDate.now()`の直接呼び出しなどはテストしにくい。DIやClock注入に直すことで、設計自体が改善されテストも書きやすくなる。

**8. テストを組み込みDB（H2）で代替してはいけない理由を説明できる**
本番と違う製品を使うと方言の違いによってテストが素通りし、本番だけで落ちる事故につながる。Testcontainersで本物のPostgreSQLを使うことでこの乖離を防ぐ。

**9. Testcontainers が何をしてくれるか、なぜ `static` にするか説明できる**
テスト実行時にDockerで本物のDBを使い捨てで自動起動してくれる。staticにするとテストクラス内で1回だけ起動して全テストで共有でき、メソッドごとに起動する重さを避けられる。

**10. CI が何をしてくれるか説明できる**
PRを作成・更新するたびに自動でビルドとテストを実行してくれる。テストが落ちているPRはマージできない設定にするのが実務の標準。

**11. セキュリティ7項目をすべて挙げられる**
①SQLは文字列連結しない、②パスワードは平文で保存しない、③秘密情報をコードに置かない、④エラー詳細を利用者に返さない、⑤ログに個人情報を出さない、⑥入力は必ず検証する、⑦ライブラリを古いまま放置しない。

**12. パスワードをハッシュ化する理由（復号できないことの意味）を説明できる**
ハッシュは一方向の変換で元のパスワードに復元できないため、DBが漏洩してもパスワード自体は守られる。照合時は入力側もハッシュ化して比較する。

**13. クライアント側のチェックだけでは不十分な理由を説明できる**
クライアント側（ブラウザ等）のコードは利用者が自由に改ざん・迂回できるため、サーバ側で必ず同じ検証を行う必要がある。
