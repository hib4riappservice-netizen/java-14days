# 第1部：教材全体の設計判断

## 判断1：「2週間で優秀な設計者」を保証しないと決めた

### 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| A | 依頼どおり「2週間で優秀な設計者になれる」と謳う | ❌ 却下 |
| B | 「不可能です」と述べて依頼を断る | ❌ 却下 |
| C | 到達可能な範囲と不可能な範囲を線引きし、前者を最大化する | ✅ 採用 |

### なぜ A を却下したか
設計スキルは「判断の引き出しの数」であり、引き出しは経験の量にしか比例しません。14日で数年分の判断経験は積めません。
**できないことをできると書けば、依頼者は現場で「話が違う」と挫折します。** 教材の役割は励ますことではなく、正しく準備させることです。

### なぜ B を却下したか
「不可能」で終わらせるのは、依頼者にとって何の価値もありません。**14日で到達できる水準は確かに存在し、それは十分に価値がある**からです。

### C の具体化
`00_はじめに` に到達する／しないを2列の表で明示。到達しない列は `06_6ヶ月ロードマップ` で回収する構造にしました。

> **この判断が、この教材の背骨です。** 正直さと有用性は両立します。

## 判断2：バラバラの練習問題ではなく、1つの成果物を14日で組み上げる構成にした

### 検討した選択肢

| 案 | 採否 | 理由 |
|---|---|---|
| 文法項目ごとの独立した練習問題 | ❌ | 「動いた」で終わり、実務との接続が見えない |
| 毎日違う小さなアプリを作る | ❌ | 「既存コードに手を入れる」という実務で最も多い作業を経験できない |
| **1つのシステム（勤怠管理API）を14日で組み上げる** | ✅ | 採用 |

### 採用理由
1. **現場で最初にやる仕事は「既存コードへの追加・修正」**です。自分が3日前に書いたコードに手を入れる経験が、これに最も近い
2. 14日目に**「動くシステム」という証拠**が残る
3. Day 1 の「計算と表示を分ける」という小さな話が、Day 10 のレイヤードアーキテクチャに直結する — **伏線を張れる**

### 題材を「勤怠管理」にした理由
- 業務ルールが適度に複雑（割増・休憩控除・雇用形態別単価）＝ ビジネスロジックを書く練習になる
- 依頼者自身がいずれ打刻する側になる＝ 仕様を直感的に理解できる
- 日本のSIerで案件数が最も多い領域の1つ
- 日時計算・金額計算・集計・境界値という**実務の落とし穴が全部入っている**

## 判断3：1日の構成を固定7ステップにした

```
①ゴール → ②新出用語 → ③座学 → ④写経 → ⑤課題 → ⑥自己チェック → ⑦予習
```

### なぜ「②新出用語」を座学の前に置いたか
依頼者は「専門的な言葉は説明されないと理解できない」と明言していました。
**説明の途中で知らない語が出ると、そこで理解が止まり、以降の説明が全部無駄になります。**
先に語彙を渡してから説明する順序が必須と判断しました。

### なぜ「④写経」でコピペを禁止したか
コピペではタイプミスが起きません。**タイプミスが起きないということは、エラーメッセージを読む練習ができない**ということです。
エラーメッセージを読む力は、現場で最も価値のあるスキルの1つであり、かつ最も訓練されていないスキルです。
**「エラーを起こさせる」ことを教材の目的に組み込みました**（Day 0 で意図的に3種類のエラーを起こさせる課題を設置）。

### なぜ「⑥自己チェック」を「説明できるか」形式にしたか
「理解した」は自己申告できてしまいます。**「口に出して30秒で言えるか」という物理的な基準**にすることで、錯覚を排除しました（最終的に174項目）。

# 第2部：レビュー時の判断

## 判断7：サブエージェントの代わりに何をするか

### 検討した選択肢

| 案 | 採否 | 理由 |
|---|---|---|
| A | 架空のレビュアーとの往復を演出する | ❌ **却下** |
| B | 「機能がないので実施できません」で終える | ❌ 却下 |
| C | 機能の不在を明示し、実体のある検証で代替する | ✅ 採用 |

### なぜ A を強く却下したか
**演出は簡単で、見栄えも良い。** 「レビュアーAより指摘」「再レビューの結果、合格」と書けば、依頼どおりに見えます。

しかしそれは**検証の実体がないのに、あるように見せる行為**です。
依頼者はこの教材に2週間を投じます。**その品質保証が演技だったと後で分かったら、教材そのものへの信頼が崩れます。**

「レビューを受けたことにする」のは、まさに教材の Day 12 で禁じている「動けばいい」「形だけ整える」という姿勢そのものです。**教材が説くことを、教材の作り手が破ってはいけない。**

### C の実装
1. **独立した批判的レビューパス** — 「この教材で学んだ新人が現場に来たら何に困るか」という、作成時とは別の観点で通読
2. **機械的検証** — 用語の未定義／リンク整合／時間配分の内部矛盾／必須警告の網羅性をスクリプト化
3. **実機検証** — 教材のコードを JDK 21 で実際にコンパイル・実行

**特に3は、私自身も結果を予測できない検証です。** これがあることで「レビューが実体を持つ」と判断しました。

## 判断8：レビューを3回で打ち切った

### 迷った点
上限は5回。あと2回できました。「指示された上限まで回すべきでは」という考えもありました。

### 打ち切った理由
第3回の検出は `[中]` 1件・`[小]` 1件で、**指摘の質が「教材の成否を左右するもの」から「体裁の細部」に落ちていました。**

ここでさらに回すと、
- 改善量に対して記述が肥大化する
- 学習者が読む量が増え、**かえって完走率が下がる**

これは実務の判断と同じです。**レビューは指摘ゼロまでやるものではなく、「残存リスクが修正コストと遅延に見合わなくなった時点」で打ち切るのが正しい運用**です。完璧を目指してリリースが遅れることは、それ自体が損失です。

この判断理由も `10_review-log.md` に明記しました。**判断の根拠を残すのが実務の作法**だからです。

// 休憩控除の境界値が、仕様書・解答例・テストの3箇所で一致するか
static int calcWorkMinutes(LocalTime in, LocalTime out){
    if(!out.isAfter(in)) throw new IllegalArgumentException("退勤は出勤より後: in="+in+", out="+out);
    int total=(int)Duration.between(in,out).toMinutes();
    int brk = total<=360 ? 0 : (total<=480 ? 45 : 60);
    return total - brk;
}

// 8時間ちょうど(09:00-17:00) → 休憩45 → 435分であるべき

# 第4部：この制作から得た教訓（依頼者へ）

この教材の制作過程は、**依頼者がこれから現場でやることの縮図**でした。参考になるはずなので残します。

| 制作で起きたこと | 現場での対応物 |
|---|---|
| 目視では気づかず、機械チェックで22語の未定義を検出 | **静的解析・自動テストは、人間が見つけられない欠陥を見つける** |
| 修正が新しい未定義語19件を生んだ | **リグレッション。だから修正のたびに再テストが必要** |
| 「解答例が無い」という致命的欠陥を、初版で見落とした | **作った本人は、自分の欠陥が見えない。だからレビューがある** |
| 「300分枠に360分の作業」という内部矛盾 | **見積りは、内訳を足し算しないと破綻に気づけない** |
| 機械の警告を1件ずつ「本物か誤検出か」判断した | **ツールの出力を鵜呑みにしない。判断は人間がする** |
| 上限5回のところ3回で打ち切った | **完璧を目指してリリースを遅らせるのも損失。打ち切り判断も仕事** |
| 「サブエージェントは使えない」と正直に書いた | **できないことを、できないと言う。これが最も重要な報告** |

> **最後の1行が、この教材で最も伝えたいことです。**
>
> 現場であなたが一番評価されるのは、難しいコードが書けることではありません。
> **「分かりません」「間に合いません」「やってしまいました」を、早く正直に言えること**です。
>
> 隠された小さな問題は、時間が経つほど巨大な事故になります。
> 正直さは、性格ではなく**技術です。** 2週間、それも一緒に身につけてください。
