# Java 14日間 実務投入プログラム — はじめに

## 0. まず、いちばん大事な話（正直に書きます）

### あなたは「地頭が良くない」のではありません
プログラミングでつまずく人の9割は、頭の良さではなく **「用語が説明されないまま話が進む」** ことでつまずいています。
この教材では、**新しい言葉が出てきたら必ずその場で日本語で定義してから使います**。分からない言葉が出てきたら、それは教材の不備です。付属の `01_glossary.md`（用語辞典）を引いてください。それでも載っていなければ、教材の欠陥として指摘してください。

### 「2週間で即戦力」の正直な定義
先に誠実にお伝えします。**2週間で「10年選手級の設計力」は手に入りません**。それは物理的に不可能で、そう言う教材は嘘です。
一方で、2週間本気でやれば **「現場の戦力として数えてもらえる状態」** には確実に到達できます。この教材はそこを狙います。具体的にはこうです。

| 到達する（14日で可能） | 到達しない（3ヶ月〜数年かかる） |
|---|---|
| 小さな機能（画面1つ／API 1本）を、仕様書から一人で実装しきれる | 数十人が使うシステム全体のアーキテクチャを一人で決める |
| 既存のコードを読んで「どこを直せばいいか」の当たりをつけられる | 大規模レガシーコードの全体最適なリファクタリング計画を立てる |
| 自分のコードに単体テストを書ける | 性能問題を本番環境のプロファイリングから特定・解決する |
| Git／プルリクエストで他人と共同作業できる | チームの技術選定・標準化を主導する |
| コードレビューの指摘を理解し、自力で直せる | 他人のコードを的確にレビューして育てる |
| 「何が分からないか」を言語化して質問できる | 顧客と要件定義の交渉をする |

**左の列ができる新人は、現場で「あいつは使える」と言われます。** これは誇張ではありません。多くの新卒は3ヶ月経っても左の列に届きません。14日で届けば、それは十分に「即戦力」です。

そして右の列は、この教材の最後にある **「15日目以降の6ヶ月ロードマップ」** で回収します。2週間はゴールではなくスタート地点です。

### 「到達したか」は感覚ではなく点数で判定します
「なんとなくできるようになった気がする」では、現場で通用するか分かりません。
本教材には **Day 7（中間）と Day 14（最終）に、点数で合否を判定するテスト** を用意しています（`09_assessment.md`）。

- **中間テスト 60点未満 → 第2週に進まないでください。** 土台が無いまま Spring Boot に触ると、必ず行き詰まります
- **最終テスト 70点以上 → 「即戦力」の合格ライン**です

このテストは、あなたを落とすためのものではありません。**「どこが穴か」を入社前に特定するため**のものです。低い点が出たら、それは失敗ではなく**成果**です。穴が見つかったのですから。

## 3. 1日の進め方（これを毎日繰り返す）

各日のページは、必ずこの順で構成されています。**この順番どおりにやってください。**

```
① 今日のゴール（3行）      ← 5分  今日終わったら何ができるか
② 新出用語（表）           ← 15分 今日出てくる言葉の意味を先に頭に入れる
③ 座学（読む）             ← 60〜90分
④ 写経ハンズオン           ← 90〜120分 サンプルを「手で」打って動かす
⑤ 課題（自力で書く）        ← 120〜180分 成果物を1歩進める
⑥ 自己チェックリスト        ← 15分  ✅が全部つかなければ翌日に進まない
⑦ 明日の予習（3行だけ）     ← 5分
```

### ④ 写経のルール（重要）
- **コピー＆ペースト禁止。必ずキーボードで打ってください。**
  理由：手で打つとタイプミスが起き、エラーメッセージを読む練習になります。**エラーメッセージを読める力は、現場で最も価値のあるスキルの1つです。** コピペではこの筋肉が鍛えられません。
- 打ち終わったら、**1行ずつ「この行は何をしているか」を声に出すか、コメントで書く**。説明できない行があれば、そこが今日の弱点です。

### ⑤ 課題のルール
- **30分ルール**：詰まったら30分は自力で考える。30分超えたら答え（解答例）を見る。
  - 30分未満で答えを見る → 力がつきません
  - 2時間粘る → 時間の無駄です。現場でも「30分詰まったら聞け」が標準ルールです
- 答えを見たら、**答えを閉じて、もう一度自力で最初から書き直す**。これをやらないと定着しません。
- **Day 6 以降は「コードの正解」ではなく「満たすべき条件」で答え合わせします**（`08_answers.md` 末尾の自己検証チェック）。設計を含む課題に唯一の正解は無く、現場のレビューも同じ形で行われるためです。

### ⑥ 自己チェックのルール
- チェック項目は「◯◯を**説明できる**」という形式です。
- **説明できる = 何も見ずに、口に出して30秒で言える**。頭の中で「なんとなく分かる」は不合格です。
- 声に出すのが恥ずかしければ、**ノートに書いてください**。書けなければ理解していません。

## 4. 学習効率を最大化する5つの技術

### ① エラーメッセージを「読む」習慣
新人とベテランの最大の差は、**エラーが出たときの行動**です。
- 新人：エラーを見た瞬間に思考停止し、コードを適当にいじる
- ベテラン：エラーメッセージを**最後まで読む**。特に「例外の種類」「メッセージ本文」「自分が書いたファイル名と行番号」の3点を探す

Javaのエラー（スタックトレースといいます）は長いですが、**あなたが見るべきは自分のファイル名が出ている最初の行だけ**です。この見方は Day 2 で徹底的にやります。

### ② 「調べ方」を先に覚える
- 公式ドキュメント（Java API仕様）を引く癖をつける。ブログより正確です
- エラーメッセージを **英語のまま** 検索する（日本語訳すると情報が激減します）
- AI に聞くときは「〜のコードを書いて」ではなく **「このエラーの意味を教えて」「このコードが何をしているか1行ずつ説明して」** と聞く。前者は学習になりませんが、後者は最高の家庭教師になります

### ③ 毎日「学習ログ」を書く（1日10分、必須）
`log/dayXX.md` に3項目だけ書いてください。
```
- 今日できるようになったこと（3つ）
- 詰まったこと・まだ分からないこと（正直に）
- 明日の最初の30分でやること
```
これは自己満足ではありません。**「分からないことを言語化する訓練」** です。現場で最も評価される新人の特徴は、「分からないことを、分かるように説明して質問できる」ことです。

### ④ 復習のタイミングを固定する（忘却対策）
人は覚えたことを1日で7割忘れます。対策は復習タイミングの固定です。
- **毎朝の最初の20分**：前日の自己チェックリストを、何も見ずに口頭で答える
- **Day 7 の午前**：Day 1〜6 のチェックリストを全部見直す
- **Day 14 の午前**：全日のチェックリストを見直す

これは既にカリキュラムに組み込んであります。飛ばさないでください。

### ⑤ 完璧主義を捨てる
- 「全部理解してから次に進む」は**やめてください**。進みません。
- Javaには「今は理解できなくていい」ものが大量にあります。教材では **【今は暗記でOK】** というマークをつけています。そこは丸暗記して先に進んでください。あとから意味が分かります。
- **動くコードを書くことが最優先**です。美しさは後から学べます。

## 5. 現場で評価される新人の条件（技術以外）

技術だけでは「即戦力」になりません。以下は Day 14 で扱いますが、**初日から意識してください**。

1. **質問がうまい** — 「動きません」ではなく「〇〇をしたら△△というエラーが出ました。□□を試しましたが同じでした。どこを見ればいいでしょうか」
2. **報告が早い** — 悪い報告ほど早く。「間に合いません」は締切当日ではなく気づいた瞬間に言う
3. **同じ質問を2回しない** — 聞いたことは必ずメモ。メモは検索できる場所に
4. **勝手に判断しない** — 仕様が曖昧なら実装前に確認する。実装後の手戻りが一番コストが高い
5. **他人のコードを尊重する** — 「このコード汚いですね」は絶対に言わない。必ず理由がある

## 7. 挫折しそうになったら

**Day 3〜5 が一番きついです。** ここでオブジェクト指向という抽象的な概念が出てきて、多くの人が「自分には向いていない」と思います。

これは全員が通る道です。**「向いていない」のではなく「まだ具体例の数が足りない」だけ**です。オブジェクト指向は、説明を読んで分かるものではなく、**手で20個くらいクラスを書いたある日、突然分かる**タイプの概念です。Day 3〜5 で分からなくても、Day 10 でSpring Bootを触ると「あ、これのことか」と繋がります。

だから **分からないまま Day 6 に進んでください。** それが正解です。
