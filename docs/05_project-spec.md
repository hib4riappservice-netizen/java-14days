## 1. このシステムは何か

中小企業（社員100〜1000人規模）の勤怠を管理するシステムの、**サーバ側（バックエンド）API** です。

画面（フロントエンド）は作りません。**画面から呼ばれる裏側の機能**を作ります。
実務では、画面担当と裏側担当が分かれていることが多く、あなたが最初に配属される可能性が高いのは裏側です。

### 誰が何のために使うか
| 利用者 | やりたいこと |
|---|---|
| 一般社員 | 出勤・退勤を打刻したい。自分の今月の勤務時間を見たい |
| 上長 | 部下の残業状況を把握したい。残業が多い人を早期に発見したい |
| 人事・労務 | 月末に全社員の勤怠を締めて、給与計算に渡したい |
| 経営 | 部署ごとの労働時間の傾向を知りたい |

### なぜこの題材なのか
1. **業務ルールが適度に複雑**：残業の割増、休憩控除、雇用形態別の単価 — 「業務ロジック」を書く練習になる
2. **誰でも仕様を理解できる**：あなた自身がいずれ打刻する側になるので、イメージしやすい
3. **実務で本当にある**：勤怠・給与・人事系のシステム開発は、日本のSIerで最も案件数が多い領域の1つ
4. **設計の勘所が詰まっている**：日時計算、金額計算、集計、権限 — 実務で必ず出る要素が揃っている

## 2. 業務用語の定義（これを先に頭に入れる）

| 用語 | 定義 |
|---|---|
| 打刻（だこく） | 出勤・退勤の時刻を記録すること |
| 所定労働時間 | 会社が定めた1日の標準勤務時間。本システムでは **8時間** |
| 法定労働時間 | 労働基準法で定められた上限。1日8時間・週40時間 |
| 残業（時間外労働） | 所定労働時間を超えた分。本システムでは1日8時間超を残業とする |
| 割増賃金 | 残業時に上乗せされる賃金。法定では **25%以上**（深夜・休日はさらに上乗せ） |
| 休憩時間 | 労働時間に含まれない時間。6時間超勤務なら45分以上、8時間超なら60分以上が法定 |
| 36協定（さぶろくきょうてい） | 残業をさせるために必要な労使協定。**月45時間・年360時間**が原則上限 |
| 締め（しめ） | 月末に勤怠を確定させ、以降変更不可にすること |
| 打刻漏れ | 出勤または退勤の打刻を忘れること。実務で頻繁に起きる |

> **【重要】この「業務用語を最初に定義する」作業は、実務でも必ずやります。**
> 開発者とお客様が同じ言葉を違う意味で使っていると、必ず手戻りが起きます。
> 用語集（ユビキタス言語と呼ばれます）を作るのは、設計の第一歩です。

## 3. 機能要件

### 3.1 社員管理

| ID | 機能 | エンドポイント | 実装Day |
|---|---|---|---|
| EMP-01 | 社員を登録する | `POST /api/employees` | Day 9-10 |
| EMP-02 | 社員を1件取得する | `GET /api/employees/{employeeId}` | Day 9-10 |

| EMP-04 | 社員情報を更新する | `PUT /api/employees/{employeeId}` | Day 11 |

**社員の項目**
| 項目 | 型 | 必須 | ルール |
|---|---|---|---|
| employeeId | 文字列 | ○ | `E` + 数字3桁（例：E001）。重複不可 |
| name | 文字列 | ○ | 100文字以内 |
| department | 文字列 | ○ | 50文字以内 |
| employmentType | enum | ○ | REGULAR / CONTRACT / PART_TIME |
| hourlyRate | 整数 | ○ | 0以上100000以下 |
| hiredDate | 日付 | ○ | 未来日不可 |
| retiredDate | 日付 | — | null なら在職中。hiredDate より後 |

### 3.2 打刻

| ID | 機能 | エンドポイント | 実装Day |
|---|---|---|---|
| ATT-01 | 打刻を登録する | `POST /api/attendances` | Day 10 |
| ATT-02 | 打刻を修正する | `PUT /api/attendances/{id}` | Day 11 |
| ATT-03 | 指定月の勤怠一覧を取得 | `GET /api/employees/{employeeId}/attendances?year=2026&month=8` | Day 10 |

**打刻の項目**
| 項目 | 型 | 必須 | ルール |
|---|---|---|---|
| employeeId | 文字列 | ○ | 存在する社員であること |
| workDate | 日付 | ○ | 未来日不可 |
| clockIn | 時刻 | ○ | — |
| clockOut | 時刻 | — | clockIn より後（null は打刻漏れ扱い） |
| breakMinutes | 整数 | — | 未指定なら自動計算（下記ルール） |

**業務ルール（ここが設計の腕の見せ所）**

| ルールID | 内容 | 違反時のHTTPステータス |
|---|---|---|
| BR-01 | 同一社員・同一日の打刻は1件のみ | 409 Conflict |
| BR-02 | 退勤時刻は出勤時刻より後であること | 400 Bad Request |
| BR-03 | 未来日の打刻は不可 | 400 Bad Request |
| BR-04 | 退職済み社員の打刻は不可 | 400 Bad Request |
| BR-05 | 存在しない社員IDでの打刻は不可 | 404 Not Found |
| BR-06 | 締め済みの月の打刻・修正は不可（**発展課題**。14日間の必須範囲外） | 409 Conflict |
| BR-07 | 1日の勤務時間が24時間を超えるものは不可 | 400 Bad Request |

**休憩時間の自動計算ルール**
```
拘束時間（退勤 − 出勤）が
  6時間以下       → 休憩 0分
  6時間超 8時間以下 → 休憩 45分
  8時間超          → 休憩 60分
実労働時間 = 拘束時間 − 休憩時間
```

> **⚠ 境界値に注意してください。** 「6時間以下」と「6時間超」の境目、ちょうど6時間0分のときどちらか。
> **仕様のこういう1文字が、実際のバグになります。** Day 7 で学んだ境界値テストを必ず書いてください。

> **【この仕様には欠陥があります。気づけましたか？】**
> 上のルールは**拘束時間**を基準に休憩を引くため、**境界をまたぐと実労働時間が逆転します**。
>
> | 拘束時間 | 休憩 | 実労働時間 |
> |---|---|---|
> | 6時間00分 | 0分 | **360分** |
> | 6時間01分 | 45分 | **316分**（44分減る） |
> | 8時間00分 | 45分 | **435分** |
> | 8時間01分 | 60分 | **421分**（14分減る） |
>
> **「1分多く働いたら、実労働が44分減る」** — 給与計算システムとしては明確な不具合です。
> 実際の労働基準法34条は**「労働時間」が6時間／8時間を超える場合**を基準にしているため、現実のシステムは逆転しない実装をします。
>
> **本教材では、この仕様のまま実装してください。** そのうえで：
> - **境界値テストで、この逆転を実際に確認する**（テストが仕様の欠陥を可視化する体験です）
> - **`attendance-api/docs/decisions.md` に「この仕様には逆転がある。実装はしたが、業務担当者に確認すべき点」と記録する**
>
> **これが実務での正しい振る舞いです。** 勝手に仕様を変えるのでも、黙って実装するのでもなく、**「仕様どおり作る／気づいた点を記録して確認する」**。
> ◆**発展**：逆転しない休憩控除（労働時間基準）に直したバージョンを別ブランチで実装し、両者の差をテストで示す。

### 3.3 月次集計（最終課題の中心）

| ID | 機能 | エンドポイント | 実装Day |
|---|---|---|---|
| SUM-01 | 社員の月次サマリを取得 | `GET /api/employees/{employeeId}/summary?year=2026&month=8` | Day 14 |
| SUM-02 | 部署の月次サマリ一覧を取得 | `GET /api/summaries?department=営業部&year=2026&month=8` | Day 14（発展） |

**各項目の定義（実装前に必ず読むこと）**

| 項目 | 定義 |
|---|---|
| `workDays` | **実労働時間を集計できた日数**。打刻漏れ（`clockOut` が null）の日は**含めない** |
| `totalWorkMinutes` | 実労働時間の合計（分）。**残業分を含む総労働時間**。休憩控除後の値 |
| `totalOvertimeMinutes` | 1日8時間（480分）を超えた分の合計（分） |
| `overtimePay` | 残業代（円）。計算式は下記 |
| `overtimeAlert` | 月間残業が45時間（2700分）を**超えた**場合に true（ちょうどは false） |
| `missingClockOutDays` | 退勤打刻が無い日の一覧 |

**レスポンス例**（時給2000円の正社員、20日出勤、うち1日が打刻漏れ）
```json
{
  "employeeId": "E001",
  "name": "田中太郎",
  "department": "営業部",
  "year": 2026,
  "month": 8,
  "workDays": 20,
  "totalWorkMinutes": 12360,
  "totalOvertimeMinutes": 2760,
  "overtimePay": 115000,
  "overtimeAlert": true,
  "alertReason": "月間残業時間が45時間を超えています",
  "missingClockOutDays": ["2026-08-14"]
}
```
**検算**：20日 × 所定8時間 = 9600分、これに残業2760分を足して 12360分。残業46時間 × 2000円 × 1.25 = 115000円。
（`workDays` が21ではなく20なのは、`missingClockOutDays` の1日を集計対象外にしているためです）

**残業代の計算ルール**
```
残業代 = 残業時間（分） ÷ 60 × 時給 × 割増率

時給   ： その社員の employees.hourly_rate を使う（§3.1 の必須項目）
割増率 ： 全雇用形態 1.25
  （労働基準法37条により、1日8時間超の時間外労働には25%以上の割増が必要。
    正社員／契約社員／アルバイトで差はつけられない）

⚠ 金額は BigDecimal で計算し、円未満は切り捨て（RoundingMode.DOWN）
```

> **【重要】計算に使う時給は、必ず社員ごとの `hourlyRate` です。** 雇用形態から時給を引かないでください。
> `EmploymentType` が持つ以下の金額は、**社員登録時に画面が出す「初期値の目安」**であって、計算の入力ではありません。
>
> | 雇用形態 | 時給の初期値（目安） |
> |---|---|
> | REGULAR（正社員） | 2000円 |
> | CONTRACT（契約社員） | 1800円 |
> | PART_TIME（アルバイト） | 1200円 |
>
> **なぜ社員ごとに持つのか**：同じ正社員でも等級や昇給で時給は違います。**「区分から金額を導出する」設計は、例外が1件出た瞬間に破綻します。**
> Day 4 の `EmploymentType` enum に時給を持たせたのは、enum の書き方を学ぶための例です。**Day 10 以降は、時給は必ずDBの `hourly_rate` から取ってください。**

**労務アラート**
```
月間残業時間が 45時間（2700分）を「超えた」場合に overtimeAlert = true
（45時間ちょうどは false ← 境界値に注意）
```
上のレスポンス例は 2760分（46時間）なので `true` になります。**2700分ちょうどなら `false` です。**

**打刻漏れの扱い**
```
clockOut が null の日は、
  - 労働時間の集計から除外する
  - missingClockOutDays に日付を入れて返す
（黙って無視せず、呼び出し側に「漏れがある」ことを伝えるのが正しい設計）
```

## 8. 発展課題（時間が余ったら／15日目以降に）

- 認証・認可（Spring Security + JWT）を追加し、本人と上長だけが勤怠を見られるようにする
